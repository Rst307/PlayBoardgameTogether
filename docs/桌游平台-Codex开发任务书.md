在线桌游平台：Codex 分阶段开发任务书 v1.1

日期：2026-09-19

**给执行开发的 Codex**

本文件是产品目标、架构约束与验收依据。请实际实现项目，不能只输出建议或演示页面。先检查工作目录、已有代码和 AGENTS.md，保留已有工作。在现有仓库内开发；若为空目录则初始化项目。未指定仓库时不要猜测远程仓库、操作其他服务器或擅自发布。

按阶段推进，每阶段先完成实现与必要验收，再进入下一阶段。一次任务未完成全部阶段时，准确更新 docs/progress.md，记录已完成内容、验证结果、阻塞项和下一步。不要把占位按钮、模拟后端、假数据和未调用成功的模型标记为完成。常规实现细节自主决定并记录；只有影响产品边界或需要缺失凭据时才提出具体问题。没有 AI 密钥仍应完成其余功能并提供可验证的模拟适配器，明确真实模型联调待完成。

**1. 项目定位与已确认目标**

建立一个浏览器在线桌游平台。平台提供账户、房间、座位、联机、权限、存档、资源管理及 AI 调度；游戏以独立扩展包提供规则、内容、布局、交互与 AI 适配。

必须支持：

- 游戏机制差异很大，不把出牌、轮流行动、资源类型或棋盘形式写死在平台。
- 图包、音效、卡牌内容、操作、棋盘布局可自定义；高级自定义允许代码实现。
- 同局真人与 AI 混合游玩，允许房间内加入 AI 座位和真人主动托管。
- 前端可单独重做；以后由不同 AI 改视觉，不应重写规则和通信。
- 支持桌面浏览器与手机浏览器，复杂桌面允许缩放和横向查看。
- 面向私人邀请游玩的小规模自部署场景起步。

UNO、波多黎各、方舟动物园只用于说明机制跨度，不代表首版要完整实现这些商业游戏。不得自动抓取或打包没有授权的商业图包、规则书；示例游戏使用原创简化规则和自制占位资源。

**2. 本轮新增的默认决策**

以下是为了让开发可执行而设置的默认方案，并非用户已经逐项确认的偏好。允许在实现前发现具体冲突后提出替代方案，不能随意扩大范围。

| 项目 | 默认方案 |
| --- | --- |
| 首版游戏模式 | 规则驱动；自由桌面和完整可视化编辑器后续实现 |
| 自定义入口 | 开发者编写可信扩展；管理员导入图包；房主选择扩展公开的游戏选项 |
| 身份 | 管理员创建本地账户，用户名和密码登录；首版不开放公众注册 |
| 房间 | 邀请码加入的私人房间，无全站公开房间目录 |
| 观战 | 首版关闭，接口预留独立观众视图；不能把任一玩家视图冒充观众视图 |
| AI 密钥 | 管理员在服务端配置，不提供前端密钥输入或展示 |
| 游戏更新 | 已开局对局锁定规则、内容及默认资源版本 |
| 断线 | 默认保留座位并等待，不自动把真人换成 AI |
| 托管 | 玩家主动开启；收回控制后递增控制器版本并废弃旧 AI 请求 |
| 撤销 | 首版不提供通用撤销；未来由游戏定义可撤销条件 |
| 暂停 | 首版无强制回合倒计时；等待型对局可以长期保存 |
| 部署 | 单台主机、单个权威 API 实例、独立 AI worker、PostgreSQL |
| 资源包 | 图片 PNG/JPEG/WebP、音频 MP3/WAV 和 JSON 映射；首版不支持 SVG/HTML/脚本上传 |
| 声音 | 首版支持自定义事件音效与独立音量；背景音乐为可选后续功能，不包含语音聊天 |

首版不包含：匹配排位、支付、语音视频、好友系统、公开插件市场、不可信代码在线上传执行、完整回放编辑器、自动从规则书生成可用游戏、通用视觉操作 AI。

**3. 架构约束**

采用模块化单体加 AI worker，不做微服务集群。候选技术默认使用 TypeScript、React、Vite、Node.js、Fastify、WebSocket、PostgreSQL、运行时 schema 校验和 pnpm workspace。执行时根据运行环境选择并锁定稳定兼容版本，不盲目使用 latest；已有项目有合适技术栈时优先沿用并记录差异。

模块建议：

- apps/web：平台页面、游戏容器与可信游戏 UI。
- apps/api：认证、房间、对局运行器、资源与管理接口。
- apps/ai-worker：领取 AI 工作、调用适配器、返回动作。
- packages/protocol：网络消息、错误码、运行时校验。
- packages/game-sdk：扩展契约与测试工具。
- packages/ui：可选卡牌、棋子、区域、计数器、选择器组件。
- packages/client-sdk：连接、恢复、发送动作和处理版本冲突。
- games/color-match：第一个原创卡牌示例。
- games/grid-garden：第二个原创空间放置示例。
- docs：架构决策、扩展开发、部署、验收与进度。

目录可适当调整，但依赖边界必须保持：规则不依赖 React、数据库或 HTTP；平台核心不引用具体游戏规则；网页构建不包含秘密状态、服务端规则或模型密钥。可信游戏注册表可以引用扩展入口，属于装配层，不是核心规则特判。

资源通过 StorageAdapter 存取，首版可以使用持久化本地卷，设计可替换为对象存储。不要为了预留接口而交付未验证的对象存储实现。任务队列首版可使用 PostgreSQL 租约任务表，不必增加 Redis。

**4. 对局运行模型**

服务端持有完整权威状态；客户端和 AI 仅持有按身份生成的视图。客户端只发送动作意图，不能直接写状态、得分或当前玩家。

游戏状态可自定义，不强制每个游戏包含 deck、hand、board 等固定字段。平台只管理对局标识、版本、扩展版本、席位、状态生命周期和持久化元信息。

每次操作顺序：认证 → 检查成员和座位控制权 → 去重 → 检查 expectedRevision → 游戏验证 → 计算转换 → 事务提交状态、记录及后续任务 → 确认成功 → 向各身份推送各自视图。

要求：

- 一局中的状态转换串行执行；数据库使用事务及版本条件更新防止丢失更新。
- 相同身份重复发送相同 requestId 和相同内容返回原结果；同 ID 不同内容返回冲突。去重在过期版本判断之前完成。
- requestId 的去重范围包含身份和对局，不能用他人的请求 ID 获取结果。
- 操作成功必须表示数据库已经提交；广播失败不撤销提交，客户端通过重新同步恢复。
- MVP 每次成功操作可以保存完整状态快照并递增 revision，不要求先实现事件溯源。
- 序列化必须规定支持的数据类型，不能依赖不可持久化的闭包、类实例或未编码 Map。
- 随机源由运行器注入，随机状态或结果与新状态一起提交；随机种子和牌堆顺序不发给玩家。
- 游戏规则不能自行调用网络、模型、系统时钟或系统随机函数。
- 如需计时，使用持久化的系统动作和截止时间；普通玩家不能构造可信系统身份。

平台支持阶段、轮流、同时提交、连续选择等流程，但由扩展维护这些规则。不要只提供一个全局 currentPlayer 字段。

同时秘密选择的默认协议：每次提交依然串行落库；另一玩家遇到旧 revision 时重新获取自身视图，并在原决策仍有效时重新提交。AI worker 可以自动重新请求，真人界面不得盲目重放有歧义的动作。初版无需复杂的多版本合并。

**5. 扩展接口的语义契约**

具体 TypeScript 签名由 Codex 制定并写入 SDK，至少提供以下职责：

| 职责 | 必要行为 |
| --- | --- |
| manifest | ID、版本、SDK 兼容范围、人数、模式、内容版本、资源包、入口声明 |
| validateOptions | 运行时校验房主选择的规则选项 |
| setup | 根据座位、选项、受控随机源创建状态 |
| getView | 为当前身份生成可公开发送的状态 |
| getActionSpec | 返回可执行的动作类型、参数结构与可见目标约束 |
| validateAction | 在真实状态中校验时机、目标、资源、权限 |
| applyAction | 返回新状态、事件及明确的后续处理需求 |
| getOutcome | 返回进行中或结束及得分/获胜者 |
| serialize/deserialize | 持久化编码、恢复校验与版本拒绝 |
| getFallbackAction | 定义 AI 失败时的合法动作；无法生成则暂停等待人工处理 |

getActionSpec 不是安全校验的替代品。复杂动作允许分步查询合法目标，不要求枚举所有参数组合。目标查询也必须以当前玩家身份过滤，不能泄露隐藏牌的存在与属性。

事件必须有明确公开范围，或由扩展提供按身份投影的事件；绝不能把含秘密信息的原始事件流广播给房间。错误消息也不能包含其他玩家手牌或完整状态。

前端交互可以先选择卡牌、再选择目标，完成后发送一个原子动作。若中间步骤必须成为游戏事实，扩展要显式存为决策状态，并定义取消与断线恢复，不能仅存在 React 本地状态。

**6. 真人、座位与 AI 控制器**

账户、房间成员、座位、控制器、连接是不同概念。至少用不同 ID 表达：accountId、roomId、seatId、matchId、connectionId。座位保留身份与资源，控制器可以是 human/script/model。

房主只管理房间，不获得私密游戏状态或任意更换别人控制器的权力。AI 座位由房主在开局前添加；真人托管由该玩家主动开启。对局中真人离开不立即释放或销毁其座位。

真人收回控制使用平台控制命令，递增 controllerEpoch；动作必须检查当前控制器类型及 epoch。AI 任务绑定 matchId、seatId、revision、decisionId 和 controllerEpoch，任何一项不再匹配则废弃结果。数据库中不能存在多个同时有效的同座位同决策任务。

同账户多标签页可读取同座位视图，修改请求统一经过版本和去重检查。不能根据客户端提交的 seatId 就授权为该座位。

AI worker 只能获得玩家视图和动作定义；不直接读取全量对局状态。任务领取通过内部认证接口完成，或使用限制权限的数据访问方案。模型适配器无权修改数据库和调用管理接口。

LLM 输入包含公开规则摘要、当前玩家视图、允许动作结构、必要的可见历史。聊天与卡牌文案作为不可信数据，不成为系统权限指令。输出经过 JSON/schema 校验与正常游戏验证。不能要求或存储模型的私密思维链；需要解释时只请求简短公开行动说明。

默认每次决策最多 1 次初始调用和 1 次修复调用，单次超时、对局预算、最大并发由管理员配置。超过预算转脚本兜底，并在界面标明实际控制器。没有合法兜底时停住并显示可理解原因，不能无限重试、跳过不允许跳过的回合或悄悄改规则。

provider 采用可替换适配器。首版提供一种真实服务适配和 mock provider；endpoint/model/key 从服务端环境读取，endpoint 不向普通用户开放。成本未知时记录 token 和调用量，不能编造金额。发送外部模型前，在托管入口说明会发送该座位可见的游戏信息。

**7. 数据与通信**

最少实体：accounts、sessions、rooms、room_members、seats、matches、match_commands、ai_jobs、game_installations、asset_packs、assets。允许合理合并。

matches 保存状态、revision、扩展和内容锁定版本；match_commands 保存去重 ID、操作者、动作、结果版本和恢复所需记录。动作本身可能包含秘密，普通客户端不能直接读取该表。

AI 租约任务要有状态、到期时间、尝试次数和去重键；worker 崩溃后可重领。外部模型调用可能因网络重试重复计费，不能宣称调用端到端恰好一次；游戏动作提交必须幂等。

HTTP 负责账户、房间、资源和管理；WebSocket 负责认证后的订阅、状态推送及动作请求，或动作经 HTTP 发送也可，但只能有一套服务端动作处理器。提供协议文档：requestId、matchId、expectedRevision、action、成功结果及稳定错误码。

断线后重新认证并获取完整玩家视图；首版不强制实现增量状态补丁。状态版本落后时不能继续基于旧界面操作。WebSocket 也要校验来源和身份、限制消息体大小与频率。

版本缺失时标记对局无法加载并说明原因，不能自动用最新版规则继续。管理员不能删除仍被活动对局引用的扩展或资源。首版不做旧存档迁移；未来迁移需显式脚本和备份。

**8. 资源包、内容和界面**

逻辑内容 ID、资源 ID、实例 ID 分离。例如同一种卡牌的多张实例共用卡面资源，但有不同实例 ID。用户换图不能改变卡牌效果。

资源包 manifest 映射稳定资源 ID 到文件，可包含 images 和 sounds，带版本、语言及各类型元信息。首版管理员上传 JSON manifest 加图片、音效文件，不需要压缩包导入；默认单文件 10 MiB、每包 100 MiB，短音效最长 15 秒，均可配置。校验实际文件类型、图片像素尺寸、音频编码与时长、文件数量、引用完整性与名称；服务端生成存储键，不采用用户提供的文件路径。音频无法解码时拒绝并说明原因。图包与音效可以分别替换映射，无需修改规则。

提供缺图占位、加载失败提示、缩略图与缓存版本。图片公开托管意味着用户可能查看所有卡牌图鉴；首版只承诺隐藏“谁持有什么、牌堆顺序”等状态秘密，不承诺隐藏素材本身。需要隐藏内容存在的特殊游戏以后使用受保护资源方案。

首版房间统一图包；个人纯视觉主题可自行切换。不同牌背不能造成额外的信息差。游戏进行中锁定规则和默认图包，不热替换。

组件库提供可选卡牌、牌堆、手牌区、区域、标记、计数器、网格和选择器，但扩展可以完全自定义 UI。平台外壳包含连接状态、玩家席位、轮到谁/待谁行动、规则说明、AI 状态和返回入口。

视觉基线：简洁桌面与清晰卡牌为中心，统一字体、间距和颜色变量；避免装饰挤占游戏区。交互必须有选中、合法目标、等待提交、失败反馈。手机操作不能仅依靠 hover 或拖拽，要提供点选替代。覆盖约 390px 手机和 1440px 桌面视口的实际检查。

建立可直接加载的 UI fixtures：初始、自己行动、他人行动、选目标、断线、AI 思考、结束。fixture 仅用于开发演示，不代替真实后端。前端改造者只修改 UI、样式和资源，若需要改协议要单独说明。

**8.1 可自定义音效**

音效属于呈现资源，不参与胜负与规则结算。游戏扩展定义“哪个可见事件对应哪个声音”，平台 AudioManager 统一负责加载、播放、音量、去重和资源释放。可信扩展也必须通过该服务播放，不能绕过用户静音设置。

- 首版事件包括出牌、摸牌、棋子落位、轮到自己、对局结束；游戏可以增加带命名空间的自定义事件。每个示例游戏至少演示一个专属音效映射。
- 配置通过稳定 soundId 指向资源，支持默认增益、优先级、冷却时间与最大同时播放数量；不允许映射中嵌入可执行脚本。数值有平台上限，游戏增益不能覆盖主音量。
- 区分本地 UI 反馈与已提交游戏事件：点击选择可以立即轻响，但“成功出牌”等声音必须在服务端确认后播放，不能让拒绝的操作听起来已成功。
- 已提交事件带稳定 eventId，例如由 matchId、revision 和事件序号组成；客户端在确认响应和广播之间按事件 ID 去重。初始快照、历史记录和重连补发不播放瞬时音效；协议明确 live 与 catch-up 来源。解锁音频后也不补播积压声音。
- 音效仅从已按玩家身份过滤的事件触发；不能向其他玩家发送带私密 soundId、隐藏牌种类或秘密选择的音频指令。秘密动作未公开时不能用不同声音、次数或时机暗示结果。
- 提供总静音、主音量、游戏音效和界面提示音量，保存在本机偏好中；房主不能强制所有人开声音。首次进入提供启用声音入口，通过用户手势初始化播放；失败显示非阻塞提示，不影响操作。
- 页面隐藏时默认停止/抑制音效，返回时只处理新的实时事件；多标签页只让可见且获得音频主控权的页面发声。后续如需后台回合提示应由用户单独开启。
- 设置短时间同类音效限流和总并发上限，避免批量发牌叠加爆音。资源缺失或加载失败静默降级；所有关键提示保留文字/视觉反馈。
- 常用短音效按需预加载，切换游戏释放不用的音频资源。音效播放失败不能回滚已提交游戏动作，也不能让客户端等待音频加载才能操作。
- AI 和真人触发相同游戏事件时使用相同声音管线；AI 不需要接收音频文件或识别声音，始终读取结构化视图。
- 使用自制或明确授权素材，资源清单记录来源和许可；不要求在线音效生成服务。

背景音乐不作为首版必交项。后续若加入，应另设 music 通道、循环与淡入淡出、独立音量和离开房间停止策略，不影响音效与规则接口。

音效验收：替换声音无需修改规则；双客户端仅合法接收者听到；相同事件重复送达只播放一次；重连和音频解锁不补播历史；静音、后台、多标签页、加载失败均不影响对局；至少实际验证一款桌面浏览器和一款手机浏览器的启用声音流程，无法测试的环境明确标记未验证。

**9. 两个原创验收游戏**

游戏 A：Color Match（轮流出牌，2–4 人）。

- 40 张牌：4 色，各含数字 1–5，每种两张；每人 5 张，翻开 1 张公共顶牌。
- 玩家可打出同色或同数字的 1 张牌，也可摸 1 张并结束回合；不能在摸牌后继续出牌。
- 无牌可摸时重洗除顶牌外的弃牌堆；仍无法摸牌则允许跳过。
- 数字 5 打出后要求选择另一位玩家，其摸 1 张；没有可用牌则不摸，不递归触发效果。
- 最后 1 张打出且效果完成后获胜；连续所有玩家都因无牌可摸而跳过时，以手牌最少者获胜，允许并列。
- 对手只看见手牌数量；提供脚本 AI、结构化模型动作和完整结束界面。
- 原创规则说明必须与实现一致，规则争议先补明确文字再编码。

游戏 B：Grid Garden（同时秘密选择＋空间放置＋资源，2–4 人）。

- 每人独立 4×4 棋盘，起始 3 点能量；共 3 轮。
- 每轮所有玩家秘密选择 harvest 或 build；提交后不能改，全部提交后统一公开。
- harvest 获得 2 点能量；build 消耗 1 点能量，并进入自己的放置阶段，将一个占相邻两格的骨牌放入棋盘，选择坐标与方向。
- 能量不足或无合法放置时不可选择 build；放置不能越界或重叠。所有需放置者完成后进入下一轮。
- 结束时每个占用格 1 分，剩余每 2 点能量 1 分，允许并列。
- 提交的选择公开前不进入其他玩家视图；棋盘公开。
- 提供简单脚本 AI；使用相同模型接口验证结构化动作不依赖卡牌。

验收重点不是游戏平衡，而是第二个游戏只通过新增扩展和注册即可工作。若平台缺少通用能力，可以修改 SDK 并记录设计原因，但禁止添加 if gameId === ... 的规则分支。两个示例不能证明所有复杂桌游已被完整支持；后续复杂游戏需要增量验证。

**10. 开发阶段与硬验收**

| 阶段 | 交付 | 必须通过的验收 |
| --- | --- | --- |
| P0 契约 | 项目骨架、依赖边界、SDK/protocol、数据库模型、架构决策 | 构建和类型检查通过，示例扩展可被注册，开发文档可启动 |
| P1 房间 | 登录、私人房间、邀请码、座位、准备、开始 | 两个独立浏览器账户加入同房；非成员无法读取房间对局；房主不能冒充其他座位 |
| P2 游戏闭环 | Color Match、私密视图、实时动作、事务保存、重连 | 真人完整结束一局；非法出牌拒绝；重复请求只结算一次；另一客户端收不到手牌；刷新后恢复 |
| P3 AI | 脚本 AI、mock/真实模型适配、队列、预算、托管 | 真人＋脚本 AI 完整一局；模拟超时和坏 JSON 可兜底；收回控制后旧 AI 结果无效；有凭据时完成真实模型联调 |
| P4 自定义 | 图片与音效资源上传与选择、AudioManager、开发 fixtures、Grid Garden | 换图不改规则；不同机制完整对局；同时选择保密；手机点选可完成放置；核心无游戏特判；完成 8.1 音效验收 |
| P5 可部署 | Docker Compose、迁移、备份恢复、健康检查、运维说明 | 新环境按 README 启动；重启恢复活动对局；备份实际恢复验证；无凭据泄露；汇总已知限制 |

每阶段文档必须写出执行过的命令和结果；未执行的验证标记未验证。不会因为“代码看起来合理”就声称通过。

核心测试集中于：规则转换、秘密隔离、重复请求、并发冲突、状态恢复、AI 过期任务与异常兜底。为持久化与权限做真实集成测试；至少一条多浏览器真人联机端到端流程。不要用大量只重复实现逻辑的浅测试代替验收。

建议额外验证：同局同时发送不同动作时只有合法动作生效；worker 提交后崩溃重领不重复执行；服务提交成功但客户端断线后重发返回同一结果；图包版本被引用时不能删除。

暂定规模目标为单 API 实例下 10 局、40 个在线连接，用本地脚本模拟合法动作并记录机器规格、错误率及处理耗时；不将此当生产容量保证，也不把外部模型响应时间计入游戏规则处理耗时。优先保证正确性，再按实际数据优化。

**11. 部署与运维要求**

- 本地 Docker Compose 至少启动 web/API、AI worker、PostgreSQL；资源目录和数据库使用持久卷。
- 提供 .env.example，不提交真实密钥；密码安全哈希，session 使用适当的安全 cookie，写请求做好 CSRF/Origin 校验。
- 管理员初始化通过一次性命令完成，不能内置公开默认密码。
- 区分存活与就绪检查；日志带 requestId/matchId，但不输出手牌、模型完整请求、密钥或会话凭据。
- 文档说明反向代理需要支持 WebSocket 和正确超时；生产环境使用 HTTPS。
- AI 服务不可用时仍可真人或脚本 AI 游玩。
- 数据备份涵盖数据库、资源和已安装扩展版本；提供恢复步骤并实际验证一次。
- 首版不宣称支持多个 API 副本；未来横向扩展需要对局所有权、跨进程广播和任务协调。
