## 1. 总体结论

目前不属于严重的“屎山”。项目的总体拆分合理，属于架构基础较好、局部实现债务比较明显的早期项目。可以继续迭代，但建议在阶段 3 正式动作与第二款游戏接入前整理关键边界。

主要问题不是目录数量不足，而是类型契约不完整、代码可读性较差，以及房间、对局、实时通信职责逐渐集中。如果直接沿用目前写法增加动作、结算、回放和更多游戏，修改影响范围会扩大。

建议保留 pnpm monorepo、模块化单体和 PostgreSQL，通过小批次重构改善维护性。现有证据不足以支持全面重写、微服务拆分或新增消息队列。

## 2. 当前结构与应保留的基础

| 位置 | 当前职责 |
| --- | --- |
| `apps/web` | React 页面、平台交互与实时订阅 |
| `apps/api` | Fastify API、认证、房间、初始对局、实时通信 |
| `packages/client-sdk` | HTTP 客户端、响应外层处理、CSRF token 管理 |
| `packages/protocol` | 部分请求、响应外层和消息 schema |
| `packages/game-sdk` | 游戏规则接口、确定性随机数、序列化和扩展契约 |
| `games/test-counter` | 演示规则及阶段 2 正式身份验收扩展 |
| `packages/ui` | 共享 UI |
| `tests` | 单元、集成和浏览器端到端测试 |

当前主要调用方向：

```text
Web → client-sdk → Fastify → AuthService / RoomService → PostgreSQL
                                       RoomService → registry → 游戏扩展
游戏扩展 → game-sdk
```

应保留的设计：

- 游戏规则不依赖 React、HTTP 或数据库；具体服务端扩展通过 registry 装配。
- 房间写入已有事务、锁、revision 检查和 request receipt 去重。
- 正式玩家身份来自 session 与固定参与者映射，区别于开发实验台的测试座位。
- 数据库约束保护实体关系，例如房间只能引用属于自己的 active match。
- 已有并发、失败回滚、私密视图和多账户流程测试，而非只有页面演示。
- 文档明确阶段 2 仅完成持久化初始对局，正式动作、回放等尚未实现；这些阶段性缺项本身不算技术债。

## 3. 问题与改进方法

优先级：P1 表示优先处理的开发风险；P2 表示有实际影响的维护性问题。优先级不等于已证实存在生产事故。

### A01：前后端类型契约未贯通（P1）

**证据**

- [client-sdk](../packages/client-sdk/src/index.ts) 的返回值主要由调用方传入泛型 `T`，内部通过类型断言返回；外层 envelope 验证不等于业务数据验证。
- [RoomPage](../apps/web/src/pages/RoomPage.tsx) 和 [MatchPage](../apps/web/src/pages/MatchPage.tsx) 使用 `any` 保存业务状态。
- `RoomSnapshot` 位于 [后端 rooms.ts](../apps/api/src/rooms.ts)，尚未作为共享通信契约使用。
- [ESLint 配置](../eslint.config.js) 全局关闭 `no-explicit-any`。

**影响**：后端修改字段或消息结构后，前端仍可能通过编译；调用者写出的泛型并不能证明服务端实际返回该形状。

**改进方法**

1. 在 `packages/protocol` 按 auth、rooms、matches、realtime 划分通信 schema 与 DTO。
2. 从 schema 推导 TypeScript 类型，服务端 DTO 投影与客户端消费共同使用。
3. SDK 方法绑定明确的请求和响应类型，避免 `room<T>()` 这类任意指定返回结构的接口。
4. 用明确的命令类型代替任意 `path + method + unknown body` 组合；允许保留私有通用请求函数。
5. 游戏专属 `view` 在平台边界保持 `unknown`，由对应扩展解析，避免把具体游戏字段放进平台公共协议。
6. 分模块收紧 `any`，不要求一次性清理所有测试和扩展内部泛型。

**验收**：房间字段改名能触发相关调用点类型错误；不合法的 WS 消息被解析边界拒绝；房间页面不再使用 `any` 作为状态类型。

### A02：核心源码过度压缩，难以阅读和审查（P2）

**证据**：[app.ts](../apps/api/src/app.ts)、[rooms.ts](../apps/api/src/rooms.ts)、[RoomPage](../apps/web/src/pages/RoomPage.tsx) 等文件存在大量长行；`app.ts` 只有约 61 行，却包含路由、连接管理、广播和清理流程。

**影响**：行数掩盖实际复杂度；断点、错误定位、代码审查和合并冲突处理成本增加。

**改进方法**：引入统一格式工具与检查脚本，先做纯格式化提交，再做职责调整。将条件、异常分支、SQL 调用和 JSX 展开到可读结构。

**验收**：格式检查可重复执行且不产生额外差异；格式化与行为改动分开审查；现有检查通过。

### A03：API 装配入口承担过多职责（P2）

**证据**：[createApp](../apps/api/src/app.ts) 同时定义 HTTP 路由、加入限流、认证 WS、订阅集合、presence、广播、撤销联动和关闭清理。

**影响**：增加正式对局订阅或修改断线策略时，需要进入同一个大函数，生命周期与业务变更容易互相影响。

**改进方法**：按 auth、rooms、matches、dev-lab 注册路由；提取 realtime 模块管理连接、订阅和定时器；`createApp` 保留依赖装配、公共错误处理及生命周期协调。实时模块通过公开接口调用认证与快照查询，不复制房间权限规则。

**验收**：保留现有 URL 和错误语义；会话撤销、重连、关闭最终快照和服务关闭清理测试通过；定时器与监听器有明确的释放入口。

### A04：房间与对局职责开始混合（P2）

**证据**：[RoomService](../apps/api/src/rooms.ts) 同时负责房间成员、座位、邀请、准备、开局写入 match、终止 match 和 `matchView`。

**影响**：阶段 3 若继续加入动作、结算和回放，该服务会成为跨生命周期的大模块。

**改进方法**

- rooms 拥有成员、座位、邀请、准备和房间状态规则。
- matches 拥有参与者、权威游戏状态、RNG、revision、动作与玩家视图。
- 先迁移 `matchView`，再为正式动作建立独立入口；开局作为协调流程连接两者。
- 开局创建对局、参与者和更新房间必须继续使用同一数据库事务；不能为了拆文件变成两个独立提交。
- SQL 可先留在所属模块内部，只在查询重复或测试边界需要时提取数据访问组件，避免为每个方法机械创建 repository。

**验收**：新增游戏动作不需修改房间座位/邀请实现；并发 start 返回同一对局；setup 失败完全回滚；关闭房间仍按现有语义终止对局；私密视图授权不变。

### A05：平台页面仍耦合演示游戏（P2）

**证据**：[MatchPage](../apps/web/src/pages/MatchPage.tsx) 直接使用 `scores`、`myHint` 等计数游戏字段；[RoomPage](../apps/web/src/pages/RoomPage.tsx) 的人数设置固定为 2；[NewRoomPage](../apps/web/src/pages/NewRoomPage.tsx) 根据具体 game ID 填入默认选项。

**影响**：接入第二款游戏时，除了新增游戏扩展，还必须改平台页面，容易积累越来越多的 game ID 条件分支。

**改进方法**：平台负责会话、连接、加载与通用错误状态；按 game ID/version 从客户端 registry 加载玩法界面。人数范围取自 manifest；配置默认值和配置界面由扩展提供最小必要接口。把房间订阅、命令提交提取为 hooks，房间页面集中展示。

**验收**：第二款游戏接入无需在平台 MatchPage 中添加专属字段；房间人数遵循当前游戏范围；不存在对应客户端版本时显示明确的不可用状态。

### A06：依赖边界检查覆盖不完整（P2）

**证据**：[check-boundaries.mjs](../scripts/check-boundaries.mjs) 写死 `games/test-counter` 的检查目录，主要通过源码字符串匹配判断依赖。

**影响**：新游戏可能未被检查覆盖；字符串检查也不能完整表达实际导入关系，因此当前 lint 通过不能证明全部模块边界正确。

**改进方法**：自动发现 `games/*` 的 client/server/shared；检查实际 import/export 依赖；规则明确禁止游戏规则依赖平台后端、前端导入服务端实现，并限制公共协议包依赖具体游戏。先覆盖实际存在的目录与依赖，不引入复杂的自研分析框架。

**验收**：任意新增游戏目录自动纳入检查；用临时违规导入验证检查会失败，移除后恢复通过。

### A07：房间快照可能跨越不同数据库状态（P1，待复现）

**证据**：[snapshot()](../apps/api/src/rooms.ts) 依次读取房间、成员、座位和扩展安装信息，默认通过连接池执行多个查询，未建立统一读取快照。

**风险**：两次读取之间有其他事务提交时，可能返回旧 `roomRevision` 与较新成员/座位数据的组合。该风险来自静态分析，本次没有并发复现，不能当作已确认事故。

**改进方法**

1. 建立可控制查询交错顺序的集成测试，验证 revision 与内容是否一致。
2. 优先评估单条 SQL 聚合读取，或在同一连接上使用只读 `REPEATABLE READ` 事务完成快照查询。
3. 仅在默认 `READ COMMITTED` 下增加 `BEGIN` 并不足以保证多次查询使用同一快照。
4. 若调用者传入已有事务连接，应明确其隔离与锁前提，避免隐式嵌套事务或擅自提交外部事务。
5. 保留广播及重连时的身份和成员校验，不以缓存替代授权。

**验收**：并发交错测试中，每个快照的 revision 与成员/座位内容来自一致状态；不引入连接泄漏或不必要的写锁。

## 4. 建议目标结构

以下是职责目标，不要求一次性创建全部目录，也不要求改变现有部署方式。

```text
apps/api/src/
  app.ts                 装配、公共错误处理、关闭协调
  auth/                  会话与认证
  rooms/                 房间规则、命令、查询、路由
  matches/               玩家视图、正式动作、对局状态
  realtime/              连接、订阅、presence、消息分发
  registry/              可信游戏扩展装配
  db/                    连接与迁移
  runtime/               现有开发实验台 runner

packages/protocol/src/
  auth.ts
  rooms.ts
  matches.ts
  realtime.ts
  index.ts

apps/web/src/
  pages/                 平台页面
  hooks/                 房间订阅与命令提交
  game-registry.ts        游戏客户端加载
```

依赖约束：路由负责传输边界，业务模块负责规则与事务；realtime 调用业务公开接口；游戏规则继续只依赖 SDK 和自身 shared 代码；平台公共协议不依赖具体游戏。

## 5. 实施顺序与检查点

| 批次 | 工作内容 | 完成条件 |
| --- | --- | --- |
| 0 | 确认版本管理与可运行基线 | 保存现状；记录类型、lint、测试结果与环境前提 |
| 1 | A02：统一格式化 | 纯格式差异，可独立审查与回退 |
| 2 | A01：共享契约和类型化 SDK | 优先贯通账户、房间、WS；类型检查与单元测试通过 |
| 3 | A07：复现并修复快照一致性风险 | 新并发测试与既有房间集成测试通过 |
| 4 | A03、A04：路由、实时通信、对局边界 | HTTP/WS 行为不变；开局原子性、授权、清理回归通过 |
| 5 | A05、A06：前端扩展接入与边界检查 | 第二款游戏可沿 registry 接入；新目录自动检查 |
| 6 | 接入阶段 3 正式动作 | 沿正式 session、参与者映射和持久化事务继续开发 |

如果 A07 提前复现为实际错误，应提前处理，不必等待全部契约整理完成。

每批只解决一类问题，避免同时修改协议、数据库结构和游戏行为。重构后再更新 [architecture.md](architecture.md)；形成新的正式架构决策时才新增或补充 ADR。本文的建议不应被误读为已经完成的架构。
