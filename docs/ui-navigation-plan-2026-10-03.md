# 平台页面职责与社交界面改进（2026-10-03）

## 现状与判断

现有好友页将好友 ID 设置、搜索、申请、好友列表、私聊和房间邀请同时展开。进入页面没有明确主任务，私聊需要越过多块管理表单；手机双列降为单列后进一步拉长。问题来自页面职责和信息层级，不只是间距或配色。

本轮沿用已有灰阶界面、React 和原生 CSS；优先改进已确认的好友流程。不因为规划就实施所有页面重构。

## 本轮页面结构

| 页面 | 主任务 | 辅助入口 |
| --- | --- | --- |
| `/friends` | 查找已有好友、查看未读、进入私聊 | 添加好友、申请、邀请、我的资料 |
| `/friends/add` | 精确搜索 ID、确认昵称、发送申请 | 分享或编辑自己的好友 ID、查看申请进度 |
| `/friends/requests` | 收到的申请：接受/拒绝；发出的申请：撤回 | 返回好友列表、添加好友 |
| `/friends/invitations` | 查看定向开桌邀请，确认加入或拒绝 | 返回好友列表；房间中仍负责发起邀请 |
| `/friends/chat/:accountId` | 阅读、发送及重试当前双方会话 | 返回好友列表、申请/邀请待处理数量 |
| 已有 `/profile` | 管理个人资料与公开好友 ID | 保留原入口，本轮没有重排 |

首页不展开任何 ID/搜索/申请/邀请/聊天表单；好友删除保留二次确认，放入每位好友的“更多”。收到申请和有效收到邀请显示待处理数量；好友入口显示总未读，列表显示每位好友未读。接受申请后提供返回列表提示，不自动跳转打断处理下一项。

私聊使用独立地址，刷新后重新验证关系并载入权威历史。非好友地址显示无法打开，不显示编辑器。消息正文和房间密码不进入 URL。继续复用现有 DirectChat 的分页、增量补取、读取水位和相同 requestId 重试；离开会话清理轮询，尚未确认的发送草稿不跨页面保存。

桌面添加页主列搜索、辅列自己的 ID；手机自然单列。导航可换行、操作至少 44px、保留原焦点和减少动态效果；不新增 UI 框架或外部字体。

## 后续规划与实施状态

按“每页一个主任务；常用任务直达；低频设置次级展开；详细工作流有独立地址和返回入口”继续评估：

1. **个人资料**：当前 ProfilePage 同时展示名片、编辑表单、好友 ID 和对局记录。建议默认展示名片与近期记录；编辑资料、ID 管理、完整对局历史分入口，避免所有表单常驻。下一轮先验收用户最常访问的资料任务和历史分页需求。
2. **候场房间（已在后续本轮实施）**：主区域聚焦座位/准备/开局；邀请、设置、规则与更多操作按需展开，建房 JSON 移入高级设置。保持原权限、revision 与事务。实际实现及验证见 [房间体验](room-page-ux-2026-10-03.md) 和 [开发进度](progress.md)。
3. **模型设置**：保留当前已有列表/编辑状态，先检查新增、编辑、测试和授权的可发现性，不机械地再拆页面。凭据操作与公开配置说明应有清楚边界，不能因界面简化隐藏真实调用结果。
4. **全站一致性**：采用统一列表标题、主按钮位置、次级导航和返回入口；标题与浏览器历史一致。后续每轮按真实流程和手机验证推进，不把“多开页面”本身作为成功标准。

## 验收标准

真实双账户完成添加→接受→私聊→刷新恢复→房间邀请；发送确认丢失不重复消息；旧注册与改名冷却流程继续有效。新增页面可直达、刷新、键盘访问和浏览器前进/后退，站内切换不请求新 HTML。首页无隐藏在下方的管理表单，320/390/768/1440px 不发生整页横向溢出；实际截图复核桌面与手机布局。实际运行结果写入开发进度，不将本文件的验收目标当作已通过事实。
