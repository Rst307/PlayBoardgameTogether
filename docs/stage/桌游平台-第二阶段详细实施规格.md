## 2. 项目方向与本阶段成果

项目最终是可编程扩展的在线桌游平台：游戏规则、操作、布局、图片和音效由扩展定义，平台提供身份、房间、权限、联机、存档和 AI 调度。后续支持真人与 AI 混合游玩。

本阶段完成后应可实际演示：管理员创建两个账户；两人分别登录；A 创建私人房间；B 用邀请码加入；两人入座并准备；A 开局；双方进入同一对局初始页面，各自只看到合法视图；非成员 C 无法访问房间和对局。

**开局的定义**：服务端校验全员准备，锁定扩展、内容与资源版本，调用 setup，持久化初始状态和参与座位，生成唯一 matchId，双方加载各自初始视图。不能只是前端跳转或修改房间状态。

正式游戏动作接口、Color Match 完整玩法在阶段 3 实现。阶段 2 的正式对局页面只展示初始视图与“玩法操作将在下一阶段接入”，不展示能点击却没有实现的出牌按钮。第一阶段开发实验台可继续在开发开关下使用，但不能当作正式对局入口。

## 5. 身份、成员、座位、连接的区分

| 概念 | 含义 | 关键规则 |
| --- | --- | --- |
| account | 持久账户 | 不等于座位或连接 |
| session | 一次登录会话 | 多会话可属于同账户 |
| room_member | 账户参加房间 | 可未入座，但本阶段不能观战 |
| seat | 房间中一个位置 | 一个账户在同房最多占一席 |
| match_participant | 开局时固定的座位与账户关系 | 后续不受成员列表改动影响 |
| connection | 一个 WS 连接 | 关闭标签页不代表退出房间 |
| controller | human/script/model | 本阶段只允许 human，不接受客户端冒充 AI |

平台 administrator 与 room host 不同。管理员本阶段仅通过本地管理命令管理账户，不自动成为房间成员，也没有读取任意私密视图的应用权限。房主可管理房间，但只能准备自己的座位，不能伪造其他人的动作。

## 6. 账户与管理员命令

### 6.1 字段与规则

- username：3–32 位 ASCII 字母、数字、下划线；大小写不敏感，以 canonical 小写列唯一。
- displayName：1–32 个 Unicode 字符，允许中文；仅作纯文本渲染，不当 HTML。
- password：默认 12–128 个 Unicode 字符，可包含空格，不自动 trim，不要求机械式字符种类组合；禁止静默截断。
- account.status：active 或 disabled。
- account.role：user 或 administrator；HTTP 普通用户不可修改角色。
- 密码使用成熟库的 Argon2id，配置按官方安全建议和运行环境校准，参数由库编码存入 hash；记录选型依据，不自制密码哈希算法。
- 数据库和日志不保存明文密码；响应永不包含 passwordHash。

### 6.2 必须提供的管理命令

| 命令职责 | 行为 |
| --- | --- |
| admin:init | 无管理员时创建首个管理员；已存在则安全退出，不重置原账户 |
| account:create | 创建普通账户，昵称可指定，密码通过隐藏提示或 stdin 输入 |
| account:reset-password | 重置指定账户密码，同时撤销其所有 session |
| account:disable / enable | 停用/启用账户；停用立即撤销会话和连接 |

命令名可沿用项目约定。密码不通过命令行参数传递，避免 shell 历史和进程列表泄露。无默认公开密码，不在生产自动生成示例账户。E2E 通过测试 fixture 创建 A/B/C，不污染开发数据库。

## 7. 会话与认证

采用 PostgreSQL 持久化、不透明随机 session token：token 使用密码学随机源，至少 32 字节，浏览器 cookie 保存原 token，数据库保存 token 摘要。不要把测试 RNG 用于 token 或邀请码。

- cookie：HttpOnly、SameSite=Lax、Path=/；生产 HTTPS 使用 Secure，本地 HTTP 只在开发允许关闭 Secure。
- 不将 token 放进 URL、localStorage、日志或 WS query。
- 默认绝对有效期 7 天，本阶段不实现复杂滑动续期；可配置。
- 登录成功生成新 session；如有当前旧 session 则撤销旧值，其他设备会话不自动撤销。
- GET me 通过 cookie 校验有效期、撤销状态、账户 active 状态。
- 登出撤销当前 session、清除 cookie，并关闭其 WS；其他 session 保持有效。
- 密码重置和账户停用撤销所有 session，在单 API 进程内立即关闭关联 WS。
- 每条有权限意义的 WS 消息和受保护 HTTP 请求重新验证 session；推送也要确认 session 有效，不能仅在握手时检查。
- 到期连接不能继续收取房间消息；设置到期关闭并在广播前校验。
- 过期 session 定期清理，定时器随应用关闭释放。

### 7.1 CSRF、来源与登录限制

同源部署为默认。所有浏览器写请求（包括登录）校验 Origin 与配置允许值，拒绝缺失或不匹配来源；受保护写请求再校验绑定 session 的 CSRF token，token 由 me/登录响应提供，通过 X-CSRF-Token 发送。CSRF token 不等于 session token。CLI 管理走本地命令，不绕过浏览器规则。

登录只接收 JSON，正文最大 16 KiB，用户名/密码校验失败返回安全错误。用户名不存在与密码错误统一 AUTH_INVALID_CREDENTIALS，尽量采用一致验证流程避免明显时序区别。

默认登录限流：每 IP 10 次失败/10 分钟、每 canonical username 5 次失败/10 分钟；达到限制返回 429 和 Retry-After。采用成熟限流组件或清晰存储逻辑，单实例内存限流可接受，文档说明重启会重置。代理来源只信任明确配置，不任意信任 X-Forwarded-For。

## 8. 房间默认规则

- 私人邀请房，无全站可枚举房间目录。
- 房间名 1–40 字，纯文本；创建时选择已安装可运行的扩展、精确版本、游戏选项和 seatCount。
- seatCount 必须在扩展人数范围内；本阶段开局要求每个配置座位都有人且准备，避免“2–4 人到底开几人”歧义。
- 容量同时限制成员数：最多 seatCount 个成员。未入座的人是候场成员，不是观众；开局前所有成员必须已入座。
- 创建者自动加入并坐第一席，默认未准备；房主也必须准备。
- 新成员默认候场，可主动占空席；房主不能替他人入座或准备。
- 同一账户可参加多个房间；单实例默认每账户最多创建 5 个未关闭房间，作为可配置资源上限。
- 房间状态 waiting、in_game、closed。结束后的再次开局不在本阶段；需要关闭旧房再创建。
- 房间不因断线、登出、标签页关闭自动销毁。

### 8.1 房间状态与允许操作

| 操作 | waiting | in_game | closed |
| --- | --- | --- | --- |
| 已有成员读取房间 | 允许 | 允许 | 允许只读关闭摘要 |
| 新成员凭邀请码加入 | 允许，需未满 | 拒绝 | 拒绝 |
| 入座、换座、离座、准备 | 允许 | 拒绝 | 拒绝 |
| 改游戏/版本/选项/人数 | 房主允许 | 拒绝 | 拒绝 |
| 主动退出房间 | 允许 | 拒绝；可以退出页面或登出，保留身份 | 可从个人列表隐藏，非本阶段必做 |
| 转让房主 | 房主向现有成员转让 | 允许，不改变对局权限 | 拒绝 |
| 关闭房间 | 房主允许 | 房主明确确认终止 | 已关闭返回相同结果 |
| 开始游戏 | 房主且通过完整校验 | 返回已有 match 或状态冲突 | 拒绝 |

关闭活动房间会将初始 match 标记 aborted，保留数据供诊断，界面确认明确提示“终止整局”。不是只关闭自己的页面。后续正式对局延续这一产品默认时需重新评估体验。

### 8.2 离开与房主转移

waiting 中主动退出释放座位、移除成员、清除所有人的准备状态。房主退出时自动转移给 joinedAt 最早的剩余成员，时间相同用 accountId 稳定排序；无人则将房间关闭。断线不触发转移。手动转移只改变管理角色，不清准备、不改变座位。

本阶段不做踢人/封禁功能，避免引入被踢者凭旧邀请码反复加入的额外规则。

## 9. 邀请码

邀请码是进入房间的共享凭证，不是账户身份或对局私密访问凭证。

- 使用密码学随机源生成 12 位 Crockford Base32 字符（约 60 位熵），界面可按 4-4-4 分组。
- 接收输入时移除分隔横线/空格并统一大写；不模糊自动纠正其他字符。
- 数据库只保存邀请码摘要、生成时间、失效时间；唯一约束，碰撞重试。
- 默认有效 24 小时；过期不移除现有成员。
- 创建或刷新邀请码时仅在该次响应向房主显示原文；房主丢失原文可刷新，旧码立即失效，不提供从 hash 还原的接口。
- 浏览器只在当前页面内存中保存原码；日志、房间广播、普通快照不含原码或摘要。
- 只有 waiting 房间可刷新/使用邀请码；已开始或关闭时失效。
- POST join body 传邀请码，不用 URL query；本阶段复制邀请码即可，不必做自动带码邀请链接。
- 加入限流默认每账户 10 次/分钟、每 IP 30 次/分钟。
- 无效、过期、不可加入的码对非成员统一 INVITE_UNAVAILABLE；不能凭错误枚举房间详情。
- 同一有效码重复加入已参加的 waiting 房间，返回已有成员快照，不再占容量。

## 10. 座位、准备和版本

seatId 为服务端 ID，seatIndex 为显示顺序。一个房间的 seatIndex 唯一，一个 accountId 在同房最多占一席。所有“我的座位”操作从当前 session 推导 accountId；body 不接受任意 ownerAccountId。

- 入座：仅 waiting、当前用户是成员、目标空席、自己尚未入座。
- 换座：一个事务内释放旧席并占新席；目标已被占则完全失败，不让用户丢失原座位。
- 离座：只释放自己的席位，仍占成员容量。
- 准备：只对自己的席位 setReady(true/false)，不能使用不幂等的 toggle。
- 改名不改变准备；改变游戏、版本、选项、人数，或成员/座位结构变化，清除全部 ready。
- 改人数仅允许目标容量不小于当前成员数，且拟删除的高位座位为空；否则拒绝，不能自动赶人或挪人。
- 修改配置先用扩展 schema 验证；更换游戏时显式使用新选项或新默认，不把旧选项盲目合并。

每个房间持久化 roomRevision；每个实质变更递增一次。准备、配置、换座等用户变更带 expectedRoomRevision；冲突返回 409 及重新获取提示，不自动重放旧决定。加入通过邀请码在锁内检查当前状态，不要求陌生人先知道 revision。

在线状态使用单独的 presenceSeq，不写入 roomRevision；否则心跳会不断使用户准备请求失效。房间版本与未来 matchRevision 也必须分开。

## 11. 事务与命令幂等

所有改变房间成员、座位、配置或生命周期的操作，在事务中先锁 room 行，再读写其成员和座位；统一锁顺序，避免跨接口不同顺序造成死锁。唯一约束作为最终防线。

不把“阶段 4 可靠性”当作本阶段不处理两人抢座、重复开局的理由。

- create、join、rotateInvite、start 等创建/发放操作携带 requestId。实现 accountId+operation+requestId 唯一的 command receipts，保存请求指纹与安全结果引用。
- 去重检查在 expectedRoomRevision 检查之前；同 ID 同内容返回既有结果，同 ID 不同内容返回 REQUEST_ID_CONFLICT。
- receipts 默认保留 7 天，明确这是幂等窗口；不无限增长。
- 不把邀请码明文、session token、私密 game state 写进普通 receipts。
- 创建/刷新邀请码原文只展示一次；若响应丢失，重复请求返回“已完成、原码不可重取”和 roomId/inviteIssuedAt，由房主确认后用新 requestId 重新刷新。不能为了精确重放而持久化明文凭证。
- 座位设置、准备等采用目标状态语义；同一请求重试按 receipts 返回原结果。没有变化的成功请求不递增 roomRevision。
- 广播只在提交成功后发生。提交后网络失败不回滚数据库，客户端重载快照；推送不是数据库真相来源。

## 12. 开局：唯一、原子、可交接

开局事务顺序：

1. 验证 session/账户、成员与房主身份。
2. 查 start receipt；匹配重试返回同一 matchId。
3. 锁 room，检查 waiting 和 expectedRoomRevision。
4. 检查所有配置座位都有活跃账户、全部 ready、无候场成员。
5. 检查游戏精确版本、SDK 兼容、内容与默认资源可解析。
6. 固定座位顺序，服务端生成 matchId、初始随机种子与 RNG 状态。
7. 调用扩展 setup，不调用外部网络；校验/序列化结果。
8. 保存 matches、match_participants、初始化状态与版本，更新 room 为 in_game、activeMatchId、roomRevision。
9. 保存 receipt，提交事务。
10. 向当前成员广播安全房间快照与 matchId；各参与者另外获取自己的 match view。

本阶段开局不以“WS 正在线”为硬前提，因为短暂断线不应破坏已准备状态；界面显示离线提示供房主判断。账户 disabled 必须阻止开局。

setup 抛错时整个事务回滚，房间保留 waiting 和原 ready；向房主返回 GAME_SETUP_FAILED，日志只记录安全定位信息。并发 start 最多生成一条对局，同房第二个不同 requestId 返回已有 matchId 或 ROOM_ALREADY_STARTED，不能生成新局。

为了保证阶段 2 可验收但不扩大到正式玩法，允许创建新的正式示例 demo.counter-room：复用第一阶段纯规则与视图逻辑，设置独立 manifest ID 和版本，生产可注册；不开放实验台身份切换。不要把原 developmentOnly 扩展的同版本 manifest 直接改成生产扩展，避免破坏不可变版本约定。

正式入口 /matches/:id 只展示服务端初始 view；不提供测试 seat query、privateHints 全表或正式动作写入口。初始化状态已经落库，因此刷新和进程重启可以重新读取相同初始视图；这不代表后续动作恢复已完成。

| 读取 match view | 否 | 否 | 否 | 仅固定参与者自己的视图 | 必须也是参与者 |
| 获取别人私密状态 | 否 | 否 | 否 | 否 | 否 |

资源不存在和无成员权限对外统一 404，避免通过 ID 探测私人房间。已在房间内但执行非房主操作返回 403。鉴权依靠 session，不依靠“这个 ID 很难猜”。

## 14. 数据库迁移

沿用 PostgreSQL 和既有 schema_migrations，不修改已应用迁移。新建以下逻辑表，已有等价实现则迁移适配。

| 表 | 关键字段与约束 |
| --- | --- |
| accounts | id、usernameCanonical UNIQUE、displayName、passwordHash、role、status、createdAt |
| sessions | id、accountId FK、tokenHash UNIQUE、csrfTokenHash 或安全绑定值、expiresAt、revokedAt、createdAt |
| rooms | id、hostAccountId FK、name、status、gameId/version、options JSONB、seatCount、roomRevision、activeMatchId、closedAt |
| room_members | roomId+accountId 主键、joinedAt；对应账户 FK |
| seats | id、roomId FK、seatIndex、ownerAccountId 可空、ready；roomId+seatIndex 唯一；非空 owner 在同房唯一 |
| room_invites | roomId 唯一、codeHash UNIQUE、expiresAt、issuedAt；只保留当前码 |
| matches | id、roomId UNIQUE（本阶段一房一局）、game/content/resource 版本、state JSONB、rngState JSONB、revision=0、status、createdAt |
| match_participants | matchId+seatId 主键、accountId、seatIndex、controllerType=human、controllerEpoch=0；match+account 唯一 |
| command_receipts | accountId+operation+requestId 唯一、requestHash、roomId 可空、resultRef、createdAt、expiresAt |

房主必须是有效成员、占座者必须是成员，可通过复合 FK/延迟约束或事务检查加测试保证。seat.ready=true 必须有 owner；rooms.seatCount 正数；revision 非负。room.activeMatchId 与 matches.roomId 对应关系必须验证，不能引用别房对局。

rooms/matches 的循环引用可用后续 ALTER TABLE 创建 FK；不要因此取消完整性检查。账户不做物理删除，停用不删除历史参与关系。结束/关闭房间保留历史，本阶段不增加自动删除功能。

索引至少覆盖 session token、有效会话到期、账户所属房间、房间成员、座位、邀请码、match 参与者与 receipts 到期。应用侧必须显式生成 DTO，禁止 SELECT * 原样返回。

## 15. HTTP 接口

沿用 /api/v1 和第一阶段 envelope、schema、traceId。请求体从 unknown 校验，拒绝未知身份字段。

| 方法与路径 | 请求/用途 | 权限 |
| --- | --- | --- |
| POST /auth/login | username、password | 来源校验、限流 |
| GET /auth/me | 当前公开账户及 CSRF 信息 | 有效 session |
| POST /auth/logout | 撤销当前 session | session、CSRF；重复登出安全成功 |
| GET /rooms | 当前用户成员房间分页列表 | session，只返回自己的 |
| POST /rooms | requestId、name、gameId/version、options、seatCount | session |
| POST /rooms/join | requestId、inviteCode | session、限流 |
| GET /rooms/:id | RoomSnapshot | 当前成员 |
| PATCH /rooms/:id/config | requestId、expectedRoomRevision、完整新配置 | 房主、waiting |
| POST /rooms/:id/invite | requestId、expectedRoomRevision | 房主、waiting，重新发码 |
| PUT /rooms/:id/my-seat | requestId、expectedRoomRevision、seatIndex | 成员、waiting，入座或换座 |
| DELETE /rooms/:id/my-seat | requestId、expectedRoomRevision（JSON body 或明确 header） | 本人、waiting |
| PUT /rooms/:id/my-ready | requestId、expectedRoomRevision、ready | 本人入座、waiting |
| POST /rooms/:id/leave | requestId、expectedRoomRevision | waiting 成员 |
| POST /rooms/:id/host | requestId、expectedRoomRevision、targetAccountId | 房主，目标为现有成员 |
| POST /rooms/:id/start | requestId、expectedRoomRevision | 房主 |
| POST /rooms/:id/close | requestId、expectedRoomRevision | 房主 |
| GET /matches/:id/view | 按 session 映射的初始视图 | 固定参与者 |

session、room、match 响应设 Cache-Control: no-store。列表默认每页 20，上限 50，使用稳定排序/游标，不提供全站成员或账户检索。

登录响应只返回公开账户字段和 CSRF token，不返回 session 明文。logout 无有效 session 时也可清 cookie 并返回成功，但仍检查 Origin。

### 15.1 RoomSnapshot

包含 id、name、status、hostAccountId、gameId/version、公开 options、seatCount、roomRevision、activeMatchId、members 的 accountId/displayName/joinedAt、seats 的 seatId/index/ownerAccountId/ready、由服务端计算的本人 permissions 和 startBlockers。

不含邀请码、码摘要、passwordHash、session、IP、数据库 state、RNG、其他人的私密视图。房间消息与对局消息分开，避免未来误把完整 state 放进通用广播。

### 15.2 错误码

新增 AUTH_INVALID_CREDENTIALS、UNAUTHENTICATED、FORBIDDEN、INVITE_UNAVAILABLE、ROOM_FULL、ROOM_NOT_WAITING、SEAT_OCCUPIED、NOT_SEATED、NOT_ALL_READY、ROOM_CONFIG_CHANGED、REQUEST_ID_CONFLICT、GAME_SETUP_FAILED、GAME_VERSION_UNAVAILABLE。沿用 VALIDATION_ERROR、STATE_CONFLICT、RATE_LIMITED 和安全 INTERNAL_ERROR。

startBlockers 用明确列表显示“尚有空座位”“某玩家未准备”“有候场成员”“扩展不可用”等；前端禁用按钮只改善体验，服务端再次完整校验。

## 16. 房间实时同步

保留第一阶段公共 ping/pong 诊断端点，但它不得接受 room.subscribe。新增 /api/v1/ws/session，用 cookie 会话认证和 Origin 校验；登录信息不从 query 获取。沿用同源开发代理与现有心跳约定。

客户端消息：room.subscribe(roomId)、room.unsubscribe(roomId)、ping。房间变更仍通过 HTTP 统一服务处理，不再另写一套 WS 修改逻辑。

服务端消息：room.snapshot、room.presence、room.closed、subscription.revoked、session.expired、pong、error。房间已开局时 snapshot 中的 activeMatchId 足够导航，可另发 match.started 通知，但不能携带完整游戏状态。

- 订阅前检查 session+成员身份；不能把 roomId 当作凭证。
- 首次订阅必须发最新快照；同一连接重复订阅不重复加入广播集合。
- 避免“读快照后才订阅”的丢消息窗口：先注册订阅并缓存期间消息，再读快照，按 roomRevision 合并；或采用等价的单实例串行方案。
- 客户端丢弃旧版本快照；收到完整新快照可直接替换，不需要应用缺失补丁。
- HTTP 响应和 WS 乱序以 roomRevision 判断，旧响应不能覆盖新状态。
- 退出成员后立即撤订阅；发送每个快照前重新确认成员和 session 有效。
- close 后向仍是成员的连接发送最终关闭快照并移除订阅。
- 重连后重新订阅、获取完整快照，不盲目重发旧准备/开局请求。
- 消息体上限、订阅数量、频率有界，错误处理不包含私人房间详情。

### 16.1 在线状态

presence 只表达连接是否在线，不代表准备、身份或入座。以账户在房间的至少一个已认证订阅连接为在线；关闭一个标签但另一个还在时仍在线。最后连接离开后默认 10 秒缓冲再显示离线，避免刷新闪烁。

使用内存 presence map + presenceSeq；服务重启后重新建立，不保存旧“在线”到数据库。不因 presence 变化清除 ready 或转移房主。客户端 WS 断开显示“连接中断，状态可能过期”，暂禁写按钮，HTTP 房间快照仍可用于恢复。

## 17. 前端页面与流程

沿用阶段 1 CSS 变量与组件，不重新换整套技术栈。UI 功能真实连接后端。

| 页面 | 本阶段内容 |
| --- | --- |
| /login | 用户名、密码、提交状态、安全错误、失败后可重试 |
| / | 登录后展示“我的房间”、创建、邀请码加入；保留游戏目录 |
| /rooms/new | 名称、游戏与版本、人数、选项、创建 |

### 17.1 房间页

- 顶部：房间名、游戏版本、人数、房主标签、连接状态。
- 主区：座位卡，显示昵称、本人、房主、准备、在线/离线；空席有入座按钮。
- 候场区：未入座成员及明确入座提示。
- 本人操作：准备/取消准备、换座、离座、退出房间，按状态显示。
- 房主操作：修改配置、刷新邀请码、转移房主、开始、关闭。
- 邀请码只有创建/刷新成功时房主看到，复制失败提供手动选择文本，不宣称复制成功。
- 修改配置会清准备，提交前说明；请求冲突时重载并要求重试，不保留错误成功状态。
- 关闭活动房间明确二次确认；普通离开页面不发送 close。
- 开局后所有客户端根据已确认的 activeMatchId 导航；网络失败用户刷新也能进入相同 match。

按钮加载时防止重复点击，但服务端仍处理并发。390px 页面使用纵向卡片，1440px 使用清晰分区；所有按钮有标签和键盘焦点，不依赖颜色/hover。密码支持粘贴和密码管理器。
