## 1. 执行前提与文档关系

第三阶段实现已按 `README.md`、`docs/progress.md`、正式动作代码和测试核对。本规格衔接《桌游平台-第二阶段详细实施规格.md》《桌游平台-第三阶段详细实施规格.md》以及既定十阶段计划。实际接口映射见 [第四阶段实施映射](../stage-4-plan.md)，本轮已执行的测试及尚未专项注入的场景见 [第四阶段验收记录](../acceptance-stage-4.md)。

本阶段目标是使已有 Color Match 真人对局在刷新、断网、重试、并发和 API 进程重启后仍然正确。沿用现有技术栈、PostgreSQL、身份系统、游戏 SDK、HTTP/WS 协议、客户端状态管理与测试框架，不重新初始化项目。

本文件中的接口名、模块名和数值为实施默认值。已有等价能力应复用；必要的小范围重构允许，但须写明原因及回归证据。若与旧文档冲突，第四阶段可靠性要求以本文件为准，游戏玩法仍以第三阶段实际已验收规则为准。

## 2. 完成后应能演示什么

两个真实账户进入同一 Color Match 对局。A 出牌后刷新仍看到正确手牌；B 短暂断网后自动恢复最新局面；重复提交同一请求不会重复摸牌；两个标签页争抢同一版本最多一个新动作生效；服务端在操作提交后、回复前被终止，重启后重试仍返回原提交结果；游戏版本缺失时明确阻止继续运行，不能偷偷换新版本恢复。

**核心承诺：在数据库成功提交且持久数据未丢失的条件下，已确认动作不丢失；同一请求最多产生一次游戏状态转换。** 网络回复可以丢失，广播可以重复，客户端必须能够通过持久化结果与最新视图收敛。

## 4. 开始前必须核对的仓库内容

1. 阅读 AGENTS.md、README、docs/progress.md、阶段 2/3 验收及交接文档；保留未提交工作。
2. 定位正式 action 路由、执行器、数据库事务、getView、事件投影、WS 订阅和前端请求状态。
3. 核对 matches 是否已有 state、rngState、revision、status、版本字段；command_receipts 是否已用于房间操作。
4. 核对第三阶段规则的实际定义：合法匹配、摸牌后是否结束回合、牌堆耗尽、数字 5 的待选目标状态、最后一张 5 的胜利时机。旧任务书未将这些细节完全写死，不得以本阶段为由重写玩法。
5. 验证所有需要恢复的信息都在序列化状态内，包括待选目标、当前阶段、随机源和终局结果，而不是只存在闭包、组件或内存定时器。
6. 记录基线构建及关键测试结果。已知失败与本次新增失败分开记录。
7. 在 docs/stage-4-plan.md 写现有接口映射、缺口、迁移方式和实施顺序。

若缺少可确认的玩法定义，优先从既有测试和已实现代码提取并记录；只有无法确定且会改变玩法的冲突才向用户提出具体问题。

## 5. 不可破坏的正确性约束

- 数据库中的已提交状态是权威来源；进程内缓存不能成为唯一存档。
- 游戏规则只在扩展中；平台不得出现针对 Color Match 出牌或胜负的特判。
- Actor 从当前会话与固定 match_participant 映射生成，客户端不能指定可信 accountId、seatId 或 controller。
- 一次成功的新动作只增加一次 match revision；拒绝或失败不增加。
- 同一个 match 的状态、RNG、revision、终态及命令成功回执必须同事务提交。
- 对外成功确认和事件推送只能发生在提交之后。
- 相同幂等键、相同请求重试返回原结果；相同键、不同请求拒绝。
- 拒绝请求不改变游戏状态、RNG 或领域事件；允许保存拒绝回执和安全诊断。
- 客户端永不收到完整 State、其他人手牌、随机源种子或内部命令日志。
- roomRevision、matchRevision、presenceSeq 是不同版本空间，不能相互替代。
- 断线不等于离座、退出、认输、转移房主或自动托管。

## 6. 存档策略：每步完整快照加命令记录

本阶段默认继续使用 matches 当前行保存最新完整快照。每次成功动作在一个事务中覆盖 state、rngState、revision 等，并保存命令回执和必要事件。读取最新快照即可恢复，不依赖重放历史动作。

这里的“操作日志”用于幂等、诊断和未来扩展；不要将它误称为已经实现完整事件溯源。暂不增加“每 N 步存一次快照再重放”的复杂恢复路径。若仓库已有完整且通过测试的等价方案，可以保留，但必须满足本文件同样的故障验收。

RNG 算法版本和内部状态必须可序列化。规则只能调用注入 RNG，不能从 Math.random、当前时间或网络取隐式输入。规则计算在克隆的 State/RNG 上完成，任何错误都丢弃副本。若旧实现存在外部时间输入，须将其作为明确、可保存的执行输入，不新增本阶段不需要的回合计时器。

完整 State 只用于服务端、数据库和受限测试；不能因为“方便排查”增加在线下载完整存档的普通用户接口。

## 7. 数据模型与约束

沿用已有表，以新增迁移补齐；不得重新创建阶段 2 已存在的 matches，不修改已应用迁移。

| 逻辑对象 | 必要字段/约束 |
| --- | --- |
| matches | id、roomId、state、rngState、rngAlgorithmVersion、revision、status、结果/结束时间、精确版本引用、updatedAt |
| 对局版本锁 | gameId/gameVersion、内容版本或 hash、资源包 ID/版本或内置标识、stateSchemaVersion、规则构建摘要 |
| match_participants | 固定 account/seat 映射；保留 controllerType、controllerEpoch |
| 对局命令回执 | matchId、actorAccountId、operation、requestId、requestHash、outcome、appliedRevision、errorCode、createdAt |
| 可选独立命令审计表 | 成功动作的服务端 actor、规范化 action、前后 revision、版本引用；仅内部读取 |
| 领域事件 | matchId、revision、eventIndex、type、内部数据/受众信息；UNIQUE(matchId,revision,eventIndex) |

可以扩展既有 command_receipts 或新增 match_command_receipts，不允许两套互相矛盾的去重权威。幂等唯一键为 (matchId, actorAccountId, operation, requestId)，operation 默认 match.action。成功命令的 appliedRevision 在同局唯一；拒绝回执没有新的 appliedRevision。

回执至少存到对局保留期结束，本阶段不自动清理对局回执。旧的房间回执 TTL 不可直接套用到活跃对局。若未来清理，必须与可重试期限一起设计，不能删掉去重记录后允许旧操作重新生效。

新增字段不得用未知版本或新随机种子伪造旧存档。能从可靠构建记录证明的版本可回填；无法确定的旧对局标记恢复阻塞并保留原始数据。新建测试数据可重建，用户已有对局不得静默重置。

## 8. 动作请求、回执与错误语义

保留第三阶段 envelope，以下为示意，实际路径与字段对齐仓库公共 schema：

```json
{
  "requestId": "client-generated-unique-id",
  "matchId": "match-id",
  "expectedRevision": 17,
  "action": { "type": "draw_card" }
}
```

同一次用户意图在首次发送前生成 requestId；网络重试必须复用原 requestId、expectedRevision 和 action。用户看到冲突后重新决定的动作使用新 requestId。

requestHash 基于 schema 校验后的规范 JSON，包含 matchId、operation、expectedRevision、action；键顺序不应导致不同 hash。拒绝未知字段，限制深度和大小。不得把 session token 放进 hash 输入或日志；actor 已由幂等键绑定。

成功回执示例：

```json
{
  "requestId": "client-generated-unique-id",
  "outcome": "accepted",
  "appliedRevision": 18,
  "duplicate": false
}
```

重试可把 duplicate 标为 true，但 appliedRevision 和原结果不变。回执不是当前视图：后来对局已到 revision 23，重试旧请求仍返回原 appliedRevision 18，客户端不能因此倒退。需要视图时另取最新、经过身份投影的快照。

| 情况 | 行为 |
| --- | --- |
| 相同幂等键与相同内容 | 返回持久化原结果，不执行规则 |
| 相同幂等键但不同内容 | REQUEST_ID_CONFLICT，409 |
| 新请求使用旧 revision | STATE_CONFLICT，409；不自动套用到新版 |
| 非法游戏动作 | 沿用游戏安全错误码，不改变状态 |
| 结束/中止后的新动作 | MATCH_NOT_ACTIVE；已成功请求重试仍可取原回执 |
| 会话失效 | UNAUTHENTICATED，401；停止自动重试 |
| 非参与者 | 沿用安全 404，不泄露对局或回执存在性 |
| 数据库暂不可用 | SERVICE_UNAVAILABLE，503，无内存回退 |
| 无法确定提交结果 | RESULT_UNKNOWN，客户端查询/同 ID 重试，不能宣称失败未执行 |
| 版本或存档不兼容 | RECOVERY_BLOCKED；参与者得到安全说明 |

有身份、合法 envelope、确定性业务拒绝可以持久化 rejected 回执，保证相同请求重试仍得同一拒绝。认证失败、格式失败不建立业务回执；数据库故障等暂态/结果未知错误不缓存为最终拒绝。

## 9. 服务端事务与同局串行处理

默认使用真实 PostgreSQL 事务与行锁作为正确性边界。进程内队列仅用于限流和减轻争抢，不能替代数据库约束。所有能够修改同局状态的路径——动作、房主关闭、中止、初始化收尾——必须遵循一致锁顺序。默认 room 行 → match 行；若现有等价策略不锁 room，须证明不会与 close/start 路径死锁或覆盖。

一次动作的处理顺序：

1. 校验请求格式、来源、会话及大小限制；解析出由服务端确定的账户。
2. 开事务，按统一顺序取锁；重新确认会话/账户有效和固定参与关系。
3. 查该 actor 的幂等键。存在时比对 hash，直接返回原结果；这一检查在 revision/终态检查前完成。
4. 对新命令检查房间/对局状态、expectedRevision、控制器权限、锁定版本可运行性。
5. 从数据库快照克隆 State/RNG，使用扩展验证并执行一次转换；不在事务里调用外部 API。
6. 校验转换后的 state schema，生成各类内部事件与结果；视图生成失败应有明确处理，不得发布半成品。
7. 原子写入 state、rngState、revision+1、终态/结果、成功回执和需要持久化的事件。结束时需改变房间状态的更新也在本事务完成。
8. COMMIT 成功后才发布通知并返回成功。内存缓存只能在提交后更新，旧缓存不得覆盖更新版本。
9. 提交前失败回滚所有领域变化；提交响应丢失时重新连接数据库查回执，查不清就返回结果未知。

执行器抛错、序列化失败、保存失败都不能消耗 RNG 或留下“只少了一张手牌”的局部变化。禁止先广播再提交，也禁止事务失败后仍返回 accepted。

本阶段只承诺单 API 进程实时推送，但并发测试必须用独立数据库连接。如果已有进程队列，不能让它掩盖缺失的数据库锁。数据库锁超时/死锁重试必须有上限，并保留原幂等键；不得无限重试。

## 10. 操作结果未知与刷新恢复

增加等价的查询能力，例如 GET /api/v1/matches/:id/commands/:requestId。只查询当前认证账户的 match.action 回执，不能通过 accountId 参数读取他人记录。

返回 accepted/rejected 回执或明确的 not_found。not_found 仅表示查询时没有可见的已提交回执，不能证明原请求不会随后提交。安全处理是：同步视图后，以完全相同的幂等键和请求重试，由数据库串行与去重决定结果。

客户端保存小型待确认记录：accountId、matchId、requestId、expectedRevision、时间及必要 action。默认 sessionStorage，限定当前标签页；不保存完整 State、他人信息、会话密钥。退出、账户切换后清除，登录初始化成功前不得自动读取并发送旧账户动作。

如动作含用户自己的私密选择，记录仅限恢复所需最小值，不进入分析埋点。若项目选择不持久化 action，则至少保存请求 ID，刷新后只能查询并明确提示用户；不能生成新 ID 悄悄重发旧意图。

状态流程：idle → submitting → accepted/rejected，或 submitting → uncertain → 查询/原 ID 重试。结果未知期间禁用该对局新的动作，提供“正在确认操作结果”和手动重新同步；超出重试次数后保持可恢复提示，不无限转圈，不显示“已失败，请再出一次”。

默认单次动作请求超时 10 秒、自动原 ID 重试最多 2 次，可配置。传输超时不代表服务端取消事务。

## 11. WS 重连与完整视图同步

沿用已认证 WS。本项目用既有 `room.subscribe` / `room.unsubscribe` 管理同房间的对局订阅，并补齐本人初始及 live `match.snapshot`；不另建平行订阅状态。动作仍走现有统一服务，不能在 WS 另写规则入口。理由见 [ADR-002](../adr/002-stage-4-match-recovery.md)。

默认恢复用完整 Player View，不要求增量补丁。本项目沿用已有 `matchId`、`revision`、`status`、本人 View、`gameId/gameVersion` 和 `delivery:'snapshot'|'live'`；初始/重同步由订阅或 HTTP 调用上下文区分，不另增来源枚举。Color Match 的当前合法动作提示在本人 View 中，与状态来自同一 revision。内容/资源版本锁在服务端 match 行，普通客户端不能修改。

订阅建立不能存在“先读快照再订阅”丢更新窗口：在同一协调器下注册并缓存更新，再读取快照并合并；或使用等价的序列化方案。客户端按 matchId、连接 generation 和 revision 过滤乱序。

- 较新完整快照直接替换；旧快照不能覆盖新快照。
- 相同 revision 的快照可用于恢复握手确认，但不重复触发一次性表现。
- 重新连接完成不等于已恢复；必须鉴权并收到当前订阅的快照后才解锁操作。
- 连接世代变化后，旧 socket 回调和旧账号 HTTP 响应不得写入当前缓存。
- 切换对局必须退订旧 match；组件卸载移除监听、重连和心跳计时器。

为处理“提交后广播失败但连接仍在线”，至少实现一种收敛机制。本阶段默认：已订阅对局每 15 秒获取一次经过鉴权的最新 revision/快照，页面重新获得焦点时立即同步。落后则重新取完整 View。可用可靠通知/outbox 代替，但不能仅依赖断线后才会触发的重连。

## 12. 连接状态、心跳与 presence

前端明确区分 connecting、syncing、online、reconnecting、offline、auth-expired、recovery-blocked。旧桌面可显示为“状态可能过期”，禁用出牌等写操作。

默认重连退避约 1、2、4、8 秒，上限 15 秒，加入随机抖动；在线后重置。浏览器离线时暂停密集尝试，上线后立即恢复。心跳沿用现有机制，参考 20 秒检查、60 秒无响应判定连接失活；后台标签页被节流时以重新同步收敛，不做游戏惩罚。

presence 只作显示。一个账户同房有多个连接时，最后连接消失才进入离线缓冲；刷新、断线、API 重启不清准备、不释放席位、不自动转主。进行中的 Color Match 等待断线玩家恢复，房主仍可按既有流程主动关闭；本阶段不自动代打、跳过或判负。

## 13. 多标签页、权限与会话撤销

同账户多标签允许观察同一本人 View；对同 revision 的两个不同新动作最多一个提交。界面按钮防抖只是体验，服务端仍需验证。

HTTP、WS 订阅、快照推送和回执查询均验证当前会话/账户和参与关系；房主、管理员都不能指定别人的 seat 查看手牌。阶段 2 的 CSRF、Origin、安全 cookie 策略继续有效。

登出、密码重置、账户停用或会话过期后停止相关推送与重试，清空私密内存缓存和待确认记录。重新登录同账户可通过服务端固定参与关系恢复座位，不能靠 localStorage 的 seatId 建立身份。

命令一旦通过事务内授权检查，随后发生的登出不保证取消正在提交的动作；文档须说明这一并发边界。撤销后新请求和后续推送必须停止，不承诺撤回已提交操作。

## 14. 服务启动、异常终止与恢复

API 启动：连接数据库 → 检查迁移兼容 → 加载 registry → 提供健康状态。默认按需读取 match，不要求把所有对局加载到内存。

恢复某局：鉴权 → 读取最新快照及版本 → 校验 schema/RNG/构建可用 → 生成本人 View → 重新订阅。绝不能调用 setup 再发一遍牌；恢复不新增 revision，不产生新领域事件，不重置 controllerEpoch。

恢复中只需加进程内加载协调，防止并发重复工作；无须在业务 status 长期写 recovering。依赖缺失是运行阻塞，不是玩家输了，保留原 active/finished/aborted 状态另报恢复错误。

正常关机停止接收新写请求，在有界时间内等待事务结束，再关闭连接池。异常终止通过数据库原子性恢复：提交前没有动作；提交后动作及回执同时存在。必须真正终止/重启子进程测试，不能只清空一个 mock 对象。

## 15. 精确版本、内容与资源锁定

对局创建时锁定精确 gameVersion、contentVersion/hash、assetPackVersion（或内置标识）、stateSchemaVersion、RNG 算法版本及规则构建摘要。不得使用 latest、^1.0 等浮动引用。

安装新版本不改变旧对局引用。相同版本号下文件摘要变化应视为不可变版本违规，拒绝静默恢复。旧版本缺失显示“该对局需要的游戏版本暂不可用”，管理员恢复对应构建后可重试，不自动改状态或调用新版反序列化。

阶段 7 尚未有资源后台时，现有内置资源清单也要有稳定标识。已被对局引用的资源/规则不得由项目清理脚本直接删除。普通单张图片加载失败可显示占位，不能因此改变规则；整个锁定包丢失时明确降级状态并禁止偷偷换包。

本阶段不要求开发通用存档升级器。必要迁移通过独立命令、备份、schema 校验和明确版本变更完成，不在普通 GET 请求中隐式迁移；没有需求时不实现。

## 16. 领域事件、历史记录与音效衔接

事件 ID 使用稳定的 (matchId,revision,eventIndex) 或等价唯一值；一个动作可能产生多个事件，不能用 revision 单独当事件 ID。客户端只接收按当前身份投影的事件，不广播内部原始记录。

快照是状态，不是“把这一局到现在发生的事件重新播放”。initial/resync 返回的历史记录仅用于文本展示，标记不可触发音效/动画。live 事件去重后才允许未来表现层消费。

重连期间发生的旧事件不补播音效；重复 WS 消息、重复 HTTP 回执、刷新页面都不能触发二次播放。事件过期不影响规则状态。私密事件的 type、payload、目标和音效线索均不得发送给无权接收者；完整 State 不能藏在通用 event.data 里。

本阶段可以用测试 spy 验证表现触发次数，不开发实际音频服务。日志补齐可取经权限过滤的历史文本；没有回放 UI，不输出他人隐藏动作作为“审计记录”。

## 17. 数据库故障、恢复阻塞与诊断

数据库不可用时只显示连接/服务异常，禁止使用旧内存状态继续落子。数据库恢复后重新加载权威状态，不把缓存全量写回。提交结果不明时查原回执，切勿自动执行补偿动作。

损坏 state、无法反序列化的 RNG、缺失版本应隔离到该局；不能导致所有房间启动失败。用户看到安全错误和重试方式，开发日志记录 matchId、traceId、错误类别，不输出手牌、牌堆或 RNG。

结构化日志建议包含 requestId、traceId、matchId、前后 revision、accepted/duplicate/conflict/rejected/unknown、事务耗时、重连/同步原因。严禁密码、token、完整 action payload、完整 View/State 默认进日志。

提供 liveness 与 readiness 区分；数据库故障 readiness 失败，不用“进程活着”冒充业务可用。故障注入钩子只在测试环境开启，不能暴露生产 HTTP 调试入口。

## 18. 前端交互验收要求

| 场景 | 用户应看到的行为 |
| --- | --- |
| 正常提交 | 按钮处理中；服务端确认后更新，不能提前显示成功 |
| HTTP 回复晚于 WS | 依据 revision 合并，不把旧状态盖回来 |
| 请求超时 | 显示正在确认结果，保留原 requestId |

## 19. 模块及文档安排

职责建议：match-command-service 负责命令事务，match-repository 负责快照/锁，receipt-repository 负责去重，match-sync 负责订阅/投影，client connection manager 负责重连，pending-command store 负责未知结果。命名对齐项目，不要求照搬新目录。

规则扩展不得 import 数据库、HTTP 或 WS；前端不得 import 服务器 State。公共 protocol 放 DTO/schema；服务器内部行类型和 RNG 不从公共包导出。HTTP 与 WS 若都支持写，必须调用同一个 service。

## 21. 故障注入与测试方法

测试使用独立 PostgreSQL 测试数据库、独立连接和 API 子进程；浏览器 A/B 使用不同 browser context，C 为非参与者。固定种子只用于测试，不输出到客户端。

设置可控测试屏障：读取/执行后提交前、COMMIT 成功后回复前、广播前、订阅注册与取快照之间。通过测试驱动精确推进，不依赖随意 sleep 碰概率。强杀测试必须记录最后已知屏障位置，避免把两种崩溃窗口混为一谈。

关键断言：state/RNG 与预期一致、revision 增量、成功回执数量、唯一事件数量、用户 View、浏览器状态不倒退。数据库层内部完整状态可在测试中比较，但不得写到公开截图或报告。

对两类会改变牌堆的操作做恢复验证，包括普通摸牌与已实现的重洗逻辑；如果第三阶段未实现重洗，使用实际规则下合法的随机转换，不擅自扩展玩法。至少覆盖待选目标和结束状态，防止只测普通回合。
