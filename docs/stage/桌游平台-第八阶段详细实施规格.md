## 1. 前提与文档关系

本规格依据总任务书中的 Grid Garden 原创规则及第七阶段交接编写。用户此前已确认第六阶段完成；本次请求编写第八阶段，不据此声称第七阶段已验收。执行开发前先核对第七阶段实际进度；缺少资源接口等必要依赖时补齐具体缺口，未完成事项如实记录。

编写时未检查仓库，不能把文中示意字段当成现有实现。沿用现有技术栈、账户/房间、SDK、持久化、控制器、模型预算、资源和音频服务，不重新初始化。新增规则必须属于 games/grid-garden；允许修订通用 SDK，但需说明原因并回归 Color Match。

## 2. 本阶段目标

完成可实际游玩的 Grid Garden：2–4 人，各有独立棋盘；每轮同时秘密选择收获或建造，全部提交后统一公开和结算；建造者各自在棋盘放置占两格的骨牌；三轮后按占格和剩余能量计分。

真人、脚本 AI 和模型控制器都通过原有统一动作系统参与；新游戏使用第七阶段图片与音效服务。用这款机制不同的游戏验证平台没有把“手牌、牌堆、单一当前玩家”写成通用前提。

完成不等于已经支持所有桌游。复杂连锁、中断窗口、竞价等仍需后续游戏逐项验证。

## 4. 开发前核对与架构缺口

读取 AGENTS.md、README、阶段 4–7 的进度、验收和交接。定位 SDK getView/actionSpec、Actor、revision、controllerEpoch、decisionKey、模型 task/attempt、事件投影、资源解析和 AudioManager。

必须查找并处理以下真实假设：只有 currentPlayerId；前端总认为有手牌；任务扫描只找一个 seat；只有出牌按钮能提交；结果只能有一个 winner；资源槽位固定卡牌；规则恢复靠前端当前页面；模型 prompt 在平台写死 Color Match。

注册表/路由装配层引用具体扩展是允许的。禁止在事务服务、权限层、调度器、预算模块加 if gameId===grid-garden 的规则特判。共享网格组件可选，不强制把所有游戏 UI 塞进一种布局。

先记录 docs/stage-8-plan.md 与基线。SDK 改动列表必须说明对旧接口的兼容/迁移方案，不能以“更通用”为由大规模无证据重构。

## 5. 完整规则：配置与开局

首个规则版本固定如下，不增加可配置回合数、棋盘大小、特殊地形或随机事件：

| 项目 | 规则 |
| --- | --- |
| 人数 | 2–4 人，沿用稳定 seatIndex |
| 棋盘 | 每人独立 4×4，共 16 格，初始全空 |
| 坐标 | x 为列、y 为行，均为整数 0–3；左上角 (0,0) |
| 初始能量 | 每人 3 点，非负整数 |
| 回合数 | 固定 3 轮，round 从 1 开始 |
| 棋子 | 不限总库存的同型骨牌，每枚占两个正交相邻格 |
| 随机性 | 本版本无需随机，不能为了用 RNG 人为加入随机规则 |
| 初始阶段 | selecting，所有席位都待秘密选择 |

棋盘与当前公开能量对所有参与者可见；当前轮的未公开选择只有本人可见。没有观战权限新增。能量不会因点击预览、请求失败或选择提交而提前扣除。

## 6. 完整规则：秘密选择

每轮每人从 harvest/build 中选择一个，并通过 submit_choice 提交。可以在本地反复改选；服务端成功保存后不可撤回、不可修改。同 requestId 重试沿用原回执；不同 ID 再提交返回 ALREADY_SUBMITTED。

- harvest 始终可选，统一公开时获得 2 点能量。
- build 仅当该玩家当前能量至少 1，且自己的棋盘至少有一个合法两格放置时可选；统一公开时扣 1 点能量。
- 尚未全员提交时，不改变任何玩家能量/棋盘，不公开选择内容。
- 可以公开谁已经提交，但只能是 hasSubmitted 布尔值/人数，不显示动作类型、专属音色、AI 提案或未来资源变化。
- 全员提交后统一公开本轮全部选择，并一次结算所有收获与建造费用；按 seatIndex 固定事件顺序，不按网络到达顺序赋予游戏优势。

服务器是可信主持，本阶段不做密码学 commit-reveal，也不宣称能向服务器运营者保密。玩家之间的保密通过服务端视图投影和无提前副作用保证。

## 7. 完整规则：空间放置

统一结算后，所有本轮选择 build 的玩家各放一枚骨牌；harvest 玩家等待。不同玩家棋盘独立，建造者可以任意先后提交，不轮流抢同一格。

动作 place_domino 包含 anchor x/y 和 orientation=H|V：H 覆盖 (x,y)、(x+1,y)；V 覆盖 (x,y)、(x,y+1)。不支持对角、反向重复编码或旋转角度任意值。横放 x 最大 2，竖放 y 最大 2，两个格都必须为空。

成功放置后本轮不能再放；棋子不可移动/撤销。能量已在统一公开时扣除，放置失败不再次扣能量，重试不再次收费。棋子实例 ID 由规则确定生成，如 round+seat 的无歧义 ID，客户端不得指定占用结果。

本人 build 资格从选择到放置期间不会失效：棋盘独立且没有别的动作能改变其棋盘，能量统一结算。若存档损坏导致无合法放置，不悄悄改为 harvest/跳过/退款；报恢复阻塞并保留状态。正常规则不会走到该异常分支。

## 8. 完整规则：轮次推进、结束与计分

所有建造者完成后自动结束本轮。若全员 harvest，无需任何人点“继续”，选择统一公开与加能量后立即推进。第 1/2 轮进入下一轮 selecting，清空新轮选择与放置标记；第 3 轮结束则 finished。

本轮结果保存在公开的 roundResults 中，即使一次提交内自动推进到下一阶段，玩家仍能看到刚才的公开选择与结算。

最终 score = occupiedCellCount + floor(energy / 2)。剩余奇数能量不加半分；最高分所有玩家并列获胜，不用 seatIndex 打破平局。返回每人的占格分、能量分、总分以及 winners 数组。终局后新游戏动作拒绝，原成功请求仍可查询回执。

可人工核对的三轮例子：

| 三轮选择 | 最终能量 | 占格数 | 分数 |
| --- | ---: | ---: | ---: |
| harvest、harvest、harvest | 9 | 0 | 4 |
| build、harvest、harvest | 6 | 2 | 5 |
| build、build、harvest | 3 | 4 | 5 |
| build、build、build | 0 | 6 | 6 |

这些规则用于验证架构，策略深度与平衡性有限。三轮正常对局最多占 6 格，满盘/无合法位置分支通常不会出现，应使用合法构造的规则单元 fixture 测边界，不能加长正式游戏来冒充规则一致。

## 9. 阶段转换与原子自动结算

持久输入阶段只有 selecting、placing、finished；reveal/能量结算是自动且有界的转换步骤，可作为事件表达，不要求增加等待动画结束的服务端阶段。

最后一位选择提交的同一事务中：保存选择 → 公开 choices → 结算全部能量 → 若有建造者进入 placing，否则推进轮次/终局。最后一次放置的同一事务中：保存棋盘 → 推进轮次/终局。一次成功外部动作仅增加一次 match revision，即使产生多个自动事件。

没有客户端 reveal、resolve、next_round 或 declare_winner 权限；不靠浏览器计时器/模型请求来继续流程。自动规则转换是有限同步计算，不在事务中等待动画或外部调用。恢复只读已提交快照，不重复发能量或重复结算。

如果仓库已有通用系统动作框架，可用等价方案，但须证明中间状态持久、后续系统动作唯一且重启可恢复。本阶段优先采用简单原子方案。

## 10. 扩展包与状态模型

建议 games/grid-garden 下包含 manifest、server rules/view/validation、shared schemas/content、client board/controls、ai script/descriptor、assets contract/default 和 tests；对齐已有目录，不另建第二套平台。

内部 State 至少包含：schemaVersion、稳定 seats、round、phase、各 seat 的 energy/board/placements、当前 secretChoices、placementDone、本轮公开结果和最终 outcome。选择未公开前只能在内部状态及本人 View 存在。

可将棋盘存为 16 格数组与 placement 列表之一作为唯一权威，另一形式由它导出；若二者均持久化，schema/恢复必须验证一致，避免棋盘显示空但实际被占。

序列化只使用约定 JSON 类型；不持久化函数、组件、DOM、定时器。恢复校验能量整数非负、坐标有效、不重叠、round/phase/提交集合一致。棋子 ID 与 seat 关系不能由客户端伪造。

## 11. Player View 与行动描述

所有参与者可见：棋盘、公开能量、round/phase、hasSubmitted、待放置席位、本轮已公开选择/历史结果、最终得分。本人额外可见自己的已提交秘密选择、是否可行动、合法动作/位置。

禁止在未公开阶段将对手选择藏在 choice:null 旁边的真实字段、事件 payload、错误、DOM、资源 key 或调试信息中；必须在服务端序列化前剔除。房主、管理员和托管控制器不能绕过 seat View。

通用 waitingForSeatIds 表达多个行动者；不要凭 currentPlayerId 推导所有权限。SDK 提供 getDecisionRequests 或等价能力，返回一组可行动 seat、稳定 decisionKey 和动作描述。

决策 key 可形如 round:1:select 与 round:1:place，按 seat 和 match 共同作用。它是规则阶段标识，不是授权凭据，也不能替代 revision/epoch 校验。

## 12. 动作协议与失败语义

沿用 envelope：requestId、matchId、expectedRevision、expectedControllerEpoch、action。选择动作示例：

```json
{ "type": "submit_choice", "round": 1, "choice": "build" }
```

放置动作示例：

```json
{ "type": "place_domino", "round": 1, "x": 2, "y": 1, "orientation": "H" }
```

上述例子仅展示形状，不保证在任意状态合法。seat 来自可信 Actor，不从 payload 取。拒绝未知字段、字符串坐标、小数、负数、越界、错误方向、错误轮次、阶段不符、重复选择/放置、无能量和重叠。

失败不改 state、RNG、revision 或事件；错误不能泄露对手选择。错误码可包括 CHOICE_NOT_ALLOWED、ALREADY_SUBMITTED、PLACEMENT_OUT_OF_BOUNDS、PLACEMENT_OVERLAP、ALREADY_PLACED、NOT_A_BUILDER、ROUND_MISMATCH，沿用统一安全 envelope。

同 ID 同内容原回执优先于当前阶段/版本检查；同 ID 不同 body 冲突。成功提交中包括自动结算时，回执 appliedRevision 与最终该次快照对应，不能向客户端伪造中间 revision。

## 13. 同时操作与全局 revision 冲突

“同时选择”表示所有玩家可在同阶段独立决定，不表示数据库同时修改同一行。继续采用同局串行事务与严格 expectedRevision，不引入多主写或无条件最后写入覆盖。

A/B 都基于 revision 10 提交时，一个先成功为 11，另一个明确 STATE_CONFLICT；失败者同步到自己的新版 View。真人保留本地待提交选择/坐标作为草稿，重新校验后提示“局面已更新，请再次确认”，用新 requestId+新 expectedRevision 提交；不在本人不知道时自动换牌/换选择。

原请求结果未知时仍按第四阶段查回执或原 ID 原 body 重试，不能将未知当明确冲突。只有确认拒绝之后，才可创建新的命令意图。不同玩家提交不能导致他人已保存秘密选择被覆盖。

选择顺序不决定奖励。将所有选择组合按不同到达顺序执行，最终 roundResults/能量/棋盘逻辑结果应相同（忽略请求 ID、时间和审计顺序）。

## 14. 多行动者与 AI 调度

调度器枚举所有行动需求：selecting 中尚未提交者；placing 中尚未放置的 build 者。每个席位仍受原 controllerType/epoch、lease、版本、预算和固定参与关系保护。

首版继续同局最多一个自动决策执行，避免多个模型相互争抢 revision 而重复付费；真人不被 AI 排队锁住，可随时提交。AI 计算必须在事务外，期间若真人使 revision 变化，旧任务仍 stale，不能凭 decisionKey 相同强行提交。

过期任务的模型结果不得直接迁到新 revision，本阶段不新增跨 revision 模型结果缓存。对旧任务的真实调用照常记账；总局预算、并发与调用上限沿用第六阶段。

为避免 stale 被扫描重建后无限反复调用，定义稳定决策组 (match,seat,epoch,decisionKey)，跨 sourceRevision 统计同一决策组的外部尝试。默认最多沿用第六阶段 2 次外部发送总上限；耗尽后，新 revision 的该组直接走新鲜合法脚本兜底，不再联网。组计数持久化，不因 task stale/重启清零；配置与已有预算原子协调。

策略界面不硬编码 card IDs，模型通过游戏 descriptor 和 choiceId 映射获得选择/放置动作。拒绝将完整棋盘 State 作为“模型需要空间推理”的理由越权传输；只用本人合法 View（本游戏棋盘公开）。

## 15. 脚本策略、候选与模型说明

基础脚本在 selecting：build 合法就 build，否则 harvest。placing：在所有合法位置中按 y、x、orientation（H 在 V 前）的稳定顺序选择第一项。策略确定性、无额外 RNG，不宣称最佳园艺规划。

fallback 采用同样受限输入生成一个合法候选；没有候选的有效 selecting 总有 harvest，placing 正常应至少有一个。若契约损坏导致空候选，blocked 并报告，不伪造 pass。

空棋盘最多 24 个合法骨牌放置（12 横+12 竖），可一次枚举，无需通用搜索服务。前后端共享几何工具可用于提示，但服务端仍最终验证；客户端候选列表不构成授权。

aiDescriptor 写明 4×4 坐标、H/V 覆盖、隐藏选择、能量、三轮和计分；给模型自己可用的 candidate IDs 和坐标描述，不把描述解析成执行代码。新游戏只添加自己的 descriptor/策略，不改供应商适配器、密钥模块或预算模型。

## 16. 恢复、托管和结束边界

选择成功刷新后，本人仍看到“已提交 build/harvest，等待其他玩家”；别人仍只有已提交标记。放置预览未提交仅为本地草稿，刷新可丢弃；已提交棋子必须恢复。

断线不自动选 harvest，不释放座位、不跳过；沿用主动托管。已秘密提交后开启托管或收回均不改变本轮选择；当前该 seat 没行动需求时 AI 不工作。进入下一决策再按控制器继续。

最后选择/最后放置提交前崩溃：整个事务不发生；提交后回复丢失：从回执与新快照恢复，能量/轮次/分数仅计算一次。房主关闭与最后动作按锁序串行，aborted 后不继续结算新动作。

同时提交、模型迟到、控制切换仍遵守 revision/epoch/lease/授权校验；不因新增游戏绕开第四至六阶段保护。

## 17. 棋盘界面与移动操作

扩展提供独立桌面布局：顶部 round/phase、本人能量与行动提示；中央本人 4×4 棋盘；侧边或下方其他玩家的公开棋盘及准备/提交状态；下方动作区与本轮结果。

selecting 显示收获 +2、建造 -1 按钮，说明成功提交后不可更改；禁用 build 时给本人可理解原因。已提交者显示等待谁，不展示他人的选择。全员公开后展示所有选择与能量变化，不需要额外“确认公开”按钮阻塞游戏。

placing 使用“选择 H/V → 点 anchor → 预览两格 → 确认放置”，并提供取消本地预览。非法格显示原因，不能只靠颜色区分；支持键盘移动/选择与明确坐标标签。拖拽可选，点选必须完整可用。

移动端约 390px 可容纳本人棋盘，其他棋盘折叠/横向查看；不能让整个页面横向溢出。确认过程中禁用重复发送，冲突后保留可辨认草稿但要求重新确认。旧 socket/请求回调不得改当前页面。

不强制动画；若有 reveal/落子动画，仅表现已提交结果。快照已经进入下一轮时动画不能继续开放上一轮按钮；减弱动画模式与静音仍能完整操作。

## 18. 图片与专属音效

新增独立 assetContract：board.grid、tile.domino、icon.energy、icon.harvest、icon.build，以及 sound.reveal、sound.place、sound.finish 等槽位；具体 key 带游戏命名空间或明确契约归属。提供原创简单默认资源包和来源说明。

复用第七阶段上传/发布/解析与 AudioManager，不新增 Grid Garden 专用文件后端/播放器。替换棋盘/棋子图片不能改变坐标、占格和合法位置，也不改变 AI prompt。

选择提交尚未公开只允许通用、相同的本地/公开提交反馈，不能按 harvest/build 播不同声音让旁人提前推断。统一公开产生一次公共 reveal cue；每次已提交落子一个 place cue；终局一个结束 cue。事件序号区分同 revision 多事件，音源上限与重连不补播保持有效。

回合自动推进可能同一 revision 多事件，客户端必须显示结果且不重复播放。完整 State、secretChoices 不能藏进资源映射或 cue payload。

## 19. 事件与数据持久化

建议事件：choice.submitted（公开仅 seat/提交状态）、choices.revealed（全部公开选择）、energy.resolved、domino.placed、round.started、match.finished。内部事件可含更多字段，但公共投影严格单独定义；提交者本人可通过 View 确认自己的秘密选择，不必在公共事件加入选择。

事件按固定 seatIndex 顺序构造，eventId 沿用 match/revision/index。roundResults 保存公开结算历史用于快照恢复，与瞬时音效解耦。最多三轮，无需新增长期回放服务。

沿用 matches.state JSONB 和原命令/事件表，不新增平台 cards/boards/garden_cells 等游戏专用业务表。如需 SDK/AI 决策组字段，用新增迁移，不修改已应用迁移。旧 Color Match 存档 schema 不变，扩展版本精确锁定，禁止静默换新版。

## 20. 可测规则不变量与 fixture

每次转换后验证：能量为非负整数；棋盘每枚骨牌恰占两个正交格且不重叠；occupiedCells=2×placements；每人每轮最多一次选择和一次建造；未公开能量不变；本轮完成后所有建造者已放；finished 只有第三轮结算完；得分公式一致。

终局若某玩家完成 b 次建造，则 harvest 次数为 3-b，energy=9-3b，occupied=2b。以独立公式核对 reducer 结果，不只复制实现当断言。

开发 fixtures 至少包含：开局；自己已提交/别人未提交；他人已提交但选择隐藏；全部 harvest 自动推进；多人 build 等待放置；边界横竖落子；重叠拒绝；最后轮并列终局；断线恢复；AI 思考/兜底；资源缺失。满盘 fixture 仅规则单元测试/开发实验台使用，不能伪造成正常三轮可达状态。

## 21. 扩展性审计交付

提交 docs/extensibility-stage-8.md，逐项列出新增的扩展代码、必要 SDK 变更与平台变更原因，证明平台未复制第二套认证/存档/任务/资源。架构检查包含依赖边界、导入路径和少量静态检查，不仅搜索 gameId 字符串就宣布通过。

必答问题：是否多行动者；规则是否自定义 JSON State；同时选择是否有私密投影；自定义棋盘 UI 是否只调用平台公共能力；模型与脚本是否共享 action；图包/声音是否可替换；旧卡牌游戏是否仍可跑。

发现接口不足时先修通用能力，保留旧适配与测试。不要为维护原 API 而把棋盘/能量塞进手牌字段，也不要为追求“零核心修改”隐藏实际缺陷。

## 24. 测试与真实模型验收边界

使用真实 PostgreSQL、独立数据库连接、2–4 个隔离 browser contexts。并发通过屏障控制；最后提交前后真实终止 API 证明事务与恢复。保密检查覆盖网络、DOM、日志、错误和音效 cue，不只看截图。

自动化可用脚本/模型 mock 跑完整三轮，检查独立计分公式与状态不变量。真实模型适配器无需因新游戏重写；有已授权配置及剩余额度时进行一次小规模真实 Grid Garden 对局或覆盖选择/放置的有限联调，记录真实模型动作与 fallback 数。

没有真实凭据则继续所有可完成项，明确“新游戏真实模型联调未执行”，不把 mock 当真实模型。本阶段扩展结构与真人/脚本验收可完成，报告中保留该验证缺口，不重复大规模付费测试。

实际音效检查需可用输出设备；无法听音或未测手机设备如实标明。每个 H 项记录通过/失败/阻塞、命令、环境和证据，不能只写测试全通过。
