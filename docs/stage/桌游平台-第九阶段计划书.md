# 桌游平台：第九阶段计划书

版本：1.1  
日期：2026-10-01  
阶段：十阶段开发计划的阶段 9——界面与操作体验完善  
交付对象：继续开发现有项目的 GPT/Codex  
执行方式：由 GPT/Codex 全程完成视觉设计、前后端调整、测试与验收

## 1. 文档关系与执行前提

本计划承接《桌游平台-分阶段开发计划》和《桌游平台-第八阶段详细实施规格》，将第九阶段细化为可执行任务。编写本文件时未检查实际仓库，因此不宣称第八阶段已经实现或验收；文中的目录、组件名和状态名均为职责示例，执行时映射到现有实现。

开发前读取 AGENTS.md、README、docs/progress.md、docs/acceptance-stage-8.md、docs/stage-9-handoff.md，以及第四至第七阶段与当前代码相关的交接文件。缺少文档时通过代码和实际运行核对，不把“没有记录”直接当成“已经完成”。

沿用现有技术栈、客户端 SDK、游戏扩展、权限、存档、AI 控制器、资源和音频服务，不重新初始化项目。早期总任务书与后续已验收规格冲突时，沿用后续规格，尤其是 AI 凭证、预算和控制权方案。

第九阶段改善两个已实现游戏及平台公共流程。发现影响游玩的具体缺陷时允许作最小修复，并记录原因、影响范围与回归证据；不能借视觉调整重写规则、事务、AI 调度或整个通信协议。

## 2. 阶段目标与范围

让玩家能够在电脑和手机上完成“登录 → 创建或加入私人房间 → 入座和准备 → 开局 → 行动或等待 → 查看结果”的完整流程，并随时知道：当前处于什么阶段、自己能做什么、正在等待谁、刚才的操作是否成功。

| 内容 | 本阶段要求 |
| --- | --- |
| 登录、大厅、房间、游戏桌面、结果页 | 统一视觉与交互，接真实数据 |
| Color Match 与 Grid Garden | 分别完善符合其机制的操作界面 |
| 手机、平板、桌面 | 完整可操作，点选不依赖拖拽 |
| 加载、空状态、失败、断线、冲突 | 明确反馈与可执行的恢复入口 |
| AI、托管、等待状态 | 展示已有真实状态，保持原权限与预算 |
| 图片、音效、动画、帮助 | 接入现有服务，提供完整文字反馈 |
| 固定开发场景与 UI 维护说明 | 必须交付，供 GPT/Codex 开发、回归和后续维护 |
| 公开房间目录、匹配、排位、好友、聊天 | 不新增 |
| 第三个游戏、自由桌面、可视化规则编辑器 | 不新增 |
| AI 解说员、语音、背景音乐、复杂特效 | 留作后续独立功能 |
| Docker、灾备、容量验收、公网发布 | 第十阶段，本阶段不执行 |

验收需要真实服务端流程。演示场景用于开发和截图，不能替代真人联机、操作恢复与权限验收。

## 3. 开发前基线与优先级

先启动现有项目，使用两个隔离账户分别完成两款游戏的基本流程；若不能完成，记录具体阻塞点。拍摄现有登录、大厅、房间、两款游戏和结果页的桌面及手机截图，建立修改前基线。

交付 docs/stage-9-plan.md，列出实际文件位置、公共组件、客户端状态来源、动作入口、待修改页面和必要依赖。将问题分为：

1. P0：无法操作、状态误导、重复提交、恢复失败或秘密泄露；先解决。
2. P1：手机布局、行动提示、错误恢复、键盘操作；进入整体视觉验收前解决。
3. P2：间距、层次、图标、轻量动画和细节；按统一设计完成。

不先做与完整流程无关的大屏展示，也不以新的静态首页代替真实房间和游戏桌面。

## 4. 视觉方向与公共组件

默认采用简洁的桌游界面：深蓝灰桌面背景、清晰的面板与卡牌、单一强调色、适度圆角和阴影。游戏卡牌的颜色、符号与资源包内容保留独立语义，不强制染成平台强调色。若已有成熟视觉系统，优先修正和补齐，避免无理由推倒重做。

先建立统一样式变量，再替换页面的重复样式。至少包括背景/面板/正文/弱化文字/边框/强调/成功/警示/错误色、字号层级、间距、圆角、阴影、层级和动画时长。间距可采用 4、8、12、16、24、32 像素的项目默认档位；具体数值可根据现有布局调整并记录。

| 公共组件职责 | 必须行为 |
| --- | --- |
| 按钮与表单 | 主次操作明确，支持加载、禁用、错误和可见焦点 |
| 对话框与抽屉 | 有标题，焦点进入并在关闭后返回，内容可滚动 |
| 页面反馈 | 统一加载、空状态、错误、重试和无权限提示 |
| 席位卡 | 区分玩家、控制器、准备、连接和等待状态 |
| 行动提示栏 | 说明当前阶段、本人任务与下一步 |
| 连接状态栏 | 显示断线、重连、恢复完成和待确认操作 |
| 通知与行动记录 | 短提示可消失，关键结果与待处理错误保持可查 |
| 声音与帮助入口 | 位置一致，可键盘访问，不遮挡主要操作 |

不为两个游戏分别复制按钮、对话框或通知系统。复杂游戏区域仍由扩展自己的客户端组件绘制，不要求所有游戏套同一种手牌布局。

## 5. 平台页面与房间流程

### 5.1 登录与大厅

登录页清楚标示字段、提交状态与错误，保留原有认证语义，不显示密码、会话凭据或内部异常。若首版没有公开注册，不添加无法工作的“注册”入口。

大厅突出“创建房间”和“使用邀请码加入”。展示本人已有权限访问的房间与恢复入口，不增加全站公开房间目录。分别设计“还没有房间”“没有可用游戏”“请求失败”的状态，不能把错误当成空列表。

创建房间表单沿用现有游戏、人数和开局选项。字段出错时在字段附近提示，提交期间阻止重复创建；加载失败后可明确重试，不自动用假数据补齐。

### 5.2 房间准备

显示房间名称、邀请码、游戏与资源包、席位和开局条件。复制邀请码应有结果提示；剪贴板失败时提供手动选择和复制方式。

本人入座、离座、准备和取消准备有明确状态。房主的添加 AI、选择资源和开局入口只在已有权限允许时出现；服务端仍作最终校验。解释无法开局的具体公开原因，例如人数不足或有人未准备。

账户、房间成员、席位和连接不混用。真人离线与 AI 思考采用不同标识；同账户多标签页不显示成多个玩家。开局条件因其他人操作改变时，同步更新，不让旧按钮继续按过期条件开局。

离开房间与结束对局分开命名。若已有关闭房间或结束对局功能，危险操作显示影响并要求明确确认；不能因为退出页面就销毁存档或释放仍在对局中的座位。

### 5.3 结果与管理页面

结果页显示真实获胜者及游戏提供的分项，不自行重新计算胜负。Grid Garden 支持多人并列；Color Match 按已有结果契约显示。返回房间、重新准备等入口仅在既有流程支持时启用，不添加占位“再来一局”。

已有资源管理或 AI 设置页使用公共组件完善反馈，不扩展上传类型、凭证授权范围或新增配置 API。普通玩家不能因前端美化获得管理员权限。

## 6. 游戏容器、行动提示与扩展边界

公共游戏容器负责页面布局、连接提示、席位、帮助、声音入口和通用状态。具体游戏负责棋盘、卡牌、局内选项、预览、说明和资源槽位。

平台可从已过滤的 Player View、公开席位状态及扩展提供的行动说明获得当前阶段、waitingForSeatIds、本人可行动状态和结果。若缺少必要公开信息，可作小范围契约补齐并回归两个游戏；不能读取完整 server State 生成提示。

| 场景 | 玩家应看到的提示示例 |
| --- | --- |
| 本人轮流行动 | “轮到你，请选择一张可出的牌。” |
| 多人秘密选择 | “第 1 轮：选择收获或建造。” |
| 本人已提交 | “你的选择已保存，等待另外 2 位玩家。” |
| 本人待放置 | “选择方向和位置，确认放置骨牌。” |
| AI 正在处理 | “正在等待 AI 作出选择。” |
| 模型转脚本兜底 | “模型暂时不可用，本次由脚本完成操作。” |
| 操作结果未知 | “尚未确认这次操作，正在查询结果。” |
| 局面更新冲突 | “局面已更新，请检查并再次确认。” |

提示文案以实际状态为准。多个待行动者不能被简化成虚假的单一“当前玩家”；自己无行动需求时不能出现可执行按钮。普通玩家只看到可公开的 AI 状态，不显示私密动作提案、提示词、供应商错误原文或密钥。

## 7. 动作提交与恢复的交互契约

这是本阶段的必要正确性要求。沿用第四至第八阶段的 requestId、revision、controllerEpoch、回执与恢复机制；UI 不另建一套动作通道。

| UI 状态 | 必须行为 |
| --- | --- |
| 本地草稿 | 可选择、预览和取消；未改变服务端事实 |
| 提交中 | 冻结此次动作内容，显示处理中，阻止同一意图重复发送 |
| 已确认成功 | 显示已保存反馈，通过新视图更新真实牌、棋子与状态 |
| 结果未知 | 保留原请求身份；查询回执或原 ID、原内容重试 |
| 明确拒绝 | 显示原因，按最新 Player View 重新校验草稿 |
| 明确版本冲突 | 同步最新视图；草稿可保留，但真人必须再次确认 |
| 已失去控制权或对局结束 | 取消无效草稿，提示原因，禁止继续提交 |

超时或断线不等于失败。未确认原请求结果前不能生成新 requestId 再执行同一意图；刷新后也沿用已有恢复机制。若发现现有实现有此缺口，作最小修复，不以禁用刷新掩盖问题。

只有确认拒绝且重新校验后，才允许用新 requestId 和新版状态提交。不得因自动重试换牌、换颜色、换目标或换坐标，也不能让真人不知情地重新作出秘密选择。

可立即显示按压、选中和本地预览；手牌移除、摸牌结果、能量变化、落子、阶段和胜负以已提交事实为准。确认成功仅表示动作已落库；不能用网络发送完成代替成功回执。

旧请求回调、旧订阅和旧动画不能修改已切换的房间、对局或账户。较旧回执可以确认其原命令，但不能将新版视图回退。账号切换后禁止重放前一账号的待确认请求，前一玩家的视图和草稿也必须清除。

## 8. Color Match 操作完善

沿用已实现规则、动作和资源契约，不增加新的卡牌效果或改变摸牌、特殊牌与终局行为。先从实际扩展确认哪些动作需要目标或颜色选择，再设计对应 UI。

手牌要求每张卡都能被识别、选中和查看。桌面可以扇形或分组排列，但不能把牌的必要信息永久遮住；手机优先使用局部横向滑动或可切换的紧凑排列。滑动区域不能导致整个页面横向溢出。

卡牌颜色同时配合符号或文字；合法提示、选中提示和禁用提示彼此不同。选中后在固定动作区显示卡牌及附加选择，完整选择后才允许确认；取消仅清除本地草稿。

摸牌等即时动作必须有清楚名称与可用条件。特殊牌的颜色或目标选择通过适配手机的面板完成，当前可选项来自本人合法视图。发生冲突时不能自动改选另一张牌。

本人手牌始终可访问，其他玩家仅显示已授权的牌背或手牌数量。出牌动画只使用允许公开的资源和信息；不得在牌背下放入对方真实卡面再靠 CSS 隐藏。

## 9. Grid Garden 操作完善

保留第八阶段固定规则：2–4 人、各自独立 4×4、初始能量 3、三轮秘密收获或建造、统一公开和结算、两格骨牌放置、并列胜利。视觉调整不能改变规则。

### 9.1 秘密选择

收获与建造按钮明确显示 +2 与 -1，说明服务端成功保存后不可修改。可以先在本地选择，再确认提交；这一确认仅提交选择，不能新增“公开”或“继续结算”的游戏动作。

未全员提交时，本人可看到自己的已保存选择，其他人仅有提交标识或人数。不能通过头像颜色、徽章、动作文案、声音、动画、资源预加载或按钮尺寸暴露他人的选择。

全员提交后展示本轮已公开结果，即使服务端已经自动进入下一轮。公共结果保留可查看入口，不要求所有玩家点“看完了”才推进规则。

### 9.2 放置与棋盘

操作为“选横向或纵向 → 点锚点格 → 预览两格 → 确认放置”，并支持取消预览。横向覆盖 (x,y) 与 (x+1,y)，纵向覆盖 (x,y) 与 (x,y+1)；左上角为 (0,0)，坐标及方向与第八阶段一致。

预览区分可用、越界与重叠，并用文字或符号解释。改变方向后重新校验，不能让上一次合法提示授权新的非法位置。服务端仍作最终校验。

本人棋盘为主要区域，其他玩家公开棋盘在侧栏、下方或折叠面板查看。不能因玩家较多把本人棋盘压缩到无法点击。已确认棋子与半透明预览明显区分；独立棋盘不画成共享争抢区域。

正常放置不能撤销或移动，取消只取消本地预览。最后一位建造者提交后规则自动推进，动画不开放上一轮操作。结果页显示占格分、能量分、总分及全部获胜者。

## 10. 响应式、触摸与键盘操作

以下宽度是本项目验收尺寸，不限定只能按这些断点编写 CSS：

| 视口 | 验收重点 |
| --- | --- |
| 320×568 | 最小手机宽度下主要操作可见、可滚动到达 |
| 390×844 | 手机完整对局的主要验收尺寸 |
| 844×390 | 横屏及较低高度，无操作区遮挡 |
| 768×1024 | 平板布局与弹层可用 |
| 1440×900 | 桌面信息层次、游戏区域与侧栏 |

桌面采用顶部状态、中央游戏区和可折叠侧栏；手机采用简短顶部信息、主要游戏区及底部动作区。手牌、对手棋盘和记录可以局部滚动；主要页面不得意外横向溢出。

底部固定栏必须为内容预留实际高度，处理安全区与浏览器工具栏，不盖住最后一张牌、棋盘底行或错误提示。加入邀请码等表单在软键盘出现时仍能访问输入、错误和提交；必要时允许页面自然滚动。

所有必须操作都有点击或触摸入口。拖拽、悬停、双击、长按和手势只能辅助，不能成为唯一入口。既有游戏若提供缩放，须有可见缩放按钮和复位入口，不能禁止浏览器的正常文字缩放。

项目默认：主要触摸按钮有效区域不少于 44×44 CSS 像素；相邻操作有合理间隔。正文与背景对比度目标至少 4.5:1，大字号文字及关键控件边界至少 3:1；这是本项目检查阈值，不在未审计时宣称已取得无障碍认证。

Tab 可到达主要入口，Enter/Space 可执行标准按钮操作，焦点可见且顺序合理。棋盘支持键盘定位和方向选择，使用真实单元格标签；对话框无焦点逃逸或陷阱，关闭后返回触发入口。

状态、错误和合法性不能只靠颜色、声音或动画表达。状态播报只传达必要公开变化，避免每次快照重播整份行动记录。字体放大到 200% 时，核心内容和动作仍可访问。

## 11. 动画、资源与音效

默认使用短促、克制的出牌、落子和公开反馈。动画用于表现已经提交的变化，规则推进不等待动画结束；关闭动画时功能和必要信息完整。

通过现有公开事件与 Player View 驱动表现，沿用 match/revision/index 等事件身份去重，不能只按 revision 去重而漏掉同次提交中的多事件。恢复快照时直接显示当前事实，不重新播放历史出牌、揭示或结束特效。

页面切换、断线恢复、终局与收到更新快照时，取消过期动画或合并表现，不让长动画队列拖住当前状态。尊重系统减弱动画设置；避免持续闪烁或必须等待的装饰效果。

复用第七阶段资源解析和 AudioManager。首次启用声音、音量、静音、失败降级、音源上限和不补播旧事件继续有效；音效无法播放时不阻塞提交。

每个关键声音都对应可见反馈。秘密选择尚未公开前，公共音效与表现不区分收获或建造。图片失败时提供带语义的占位，仍能区分卡牌、坐标和操作；资源包替换不改变命中区域、占格逻辑或规则。

## 12. 加载、异常与帮助

| 状态 | 展示与恢复要求 |
| --- | --- |
| 首次加载 | 与最终布局相近的占位；不把加载显示为空房间 |
| 无房间或无资源 | 解释原因，提供当前权限允许的下一步 |
| 网络错误 | 显示重试入口，保留可恢复的输入 |
| 断线与重连 | 标明当前不可提交；重新认证并同步后再开放操作 |
| 操作结果未知 | 持续显示查询状态，不用短暂通知冒充失败 |
| 版本冲突 | 保留可辨认草稿，按新视图提示再次确认 |
| 会话过期 | 按既有安全规则回到登录和恢复流程，不丢弃服务端对局 |
| 无权限或房间关闭 | 清楚解释，提供返回入口，不继续访问旧订阅 |
| 游戏/资源版本不可用 | 显示明确阻塞，不悄悄换版本或重开 |
| 扩展 UI 渲染错误 | 隔离该区域，允许重试和返回，不擅自修改规则状态 |

重要错误保持可见到处理完成，普通成功反馈可以短暂显示。展示稳定、可理解的错误文案，开发诊断不混入玩家界面；日志不得含秘密状态或凭据。

两款游戏分别提供简短规则、目标、当前阶段操作说明、计分和特殊操作帮助。说明以实际扩展版本为准；不要将服务端实现细节、revision 或租约概念写给普通玩家。

在托管和模型配置已有流程中，保留外部模型会接收该席位可见信息的说明。是否正在托管、能否收回控制、模型是否转脚本均使用真实状态，不编造进度条、思考秒数或费用。

## 16. 验证方法与证据要求

优先复用已有浏览器自动化、集成和截图工具，不为本阶段无理由迁移测试框架。使用真实 API 和数据库，至少两个隔离 browser contexts；不同账户不能共享会话来冒充多人。

必要验证分四组：

1. 真实端到端：两游戏分别在桌面和手机尺寸完成从登录/入房到结束的对局；覆盖原有合法特殊操作以及 Grid Garden 三轮与并列。
2. 可靠性：可控制造回复丢失、网络中断、版本冲突、控制权改变和旧回调；通过服务端快照与回执证明没有重复执行，不能仅凭截图断言。
3. 隐私与权限：检查网络响应、DOM、行动记录、资源请求及表现数据。秘密未公开时无他人选择或真实手牌，账户切换后无旧数据残留。
4. 视觉与输入：按视口矩阵检查溢出、遮挡、长文本、软键盘、键盘焦点、放大、静音和减弱动画，保存关键修改前后截图。

截图至少覆盖大厅、四人准备房间、Color Match 长手牌、Grid Garden 放置预览、多等待者、冲突、断线和并列结果；主要页面有桌面及 390px 手机版本。截图使用匿名场景，避免暴露邀请码、真实账号或凭据。

手机尺寸模拟通过不等于真机通过。条件允许时，在真实 iOS 浏览器和桌面 Chromium 上做最小人工流程，并记录系统、浏览器、输入方式与结果；没有真机就明确记录缺口，继续其余验收。

音效需要实际输出条件验证；无法听音则标明。AI 状态 UI 可通过脚本与 mock 验证，mock 不算真实模型联调；纯前端改动不要求重复大规模付费对局。缺少模型凭据时继续可执行部分，继承并明确记录前序真实联调缺口。

记录动作反馈、页面滚动或动画存在的实际性能问题，定位后作针对性优化。不能用开发场景的加载速度声称生产容量；多房间负载、部署和备份仍交第十阶段。
