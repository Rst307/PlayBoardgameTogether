版本：1.0  
日期：2026-09-25

## 1. 执行前提与文档关系

用户已确认第四阶段完成。本文件承接第四阶段的事务存档、命令去重、版本锁定、身份投影和恢复机制。编写时已读取第四阶段规格，但未查看实际仓库、未替用户验收第四阶段代码。执行开发前必须核对实际实现。

沿用现有技术栈、PostgreSQL、游戏 SDK、Color Match 规则、认证、房间和前端。不重新初始化、不另造 AI 专用游戏引擎。接口名和默认参数可按仓库等价映射，必要调整记录到 docs/decisions.md。

本阶段的 AI 指服务器运行的内置程序策略，无外部模型调用、无 API 密钥、无费用。目标是可靠接入和公平操作，不承诺高水平博弈。

## 2. 阶段目标与可演示成果

完成后，一名真人可以创建房间、添加一至三个脚本 AI，并完整玩完 Color Match。真人可主动开启自己座位的托管，随后收回控制；正在计算或已经排队的旧 AI 结果不能在收回后继续生效。API 重启后，仍有 AI 行动需求的对局自动继续，不依赖有人打开页面。

必须演示：真人与 AI 混合对局；真人中途托管和收回；待选目标阶段切换控制；AI 超时/输出非法时合法兜底；提交成功但调度器没收到结果时恢复，且不重复出牌。

## 5. 四个必须分开的概念

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| 座位 | 游戏规则中的稳定身份 | seat-2 |
| 所有者 | 座位原本归属；决定真人查看和收回权限 | A 账户，或无真人所有者的 bot |
| 控制器 | 当前谁能提交新游戏动作 | human 或 script |
| 控制世代 controllerEpoch | 控制授权每次改变时递增的整数 | 0 → 1 → 2 |

真人开启托管后，ownerAccountId 和固定参与关系不变，仍看到自己的手牌；只是当前 controllerType=script。内置 AI 座位没有可登录的账户，不创建共享 bot 密码，也不借用房主账户冒充 AI。

专用 AI 座位开局后不能被房主“收回”成自己的第二席。中途换玩家、替换 AI 座位为真人不在本阶段。

## 6. 房间、AI 席位与准备规则

在 waiting 房间中，只有房主可向空席添加 AI 或移除已有专用 AI。不能覆盖真人席位，不能借添加 AI 踢人。AI 名称由服务端生成，如“电脑 1”，显式标注“脚本 AI”。

沿用配置 seatCount 和游戏人数限制。AI 占一个席位并计入游戏人数，不作为真实 room_member，不产生会话、邀请码、presence。真人成员总数加专用 AI 数不得超过 seatCount；加入、添加 AI 和抢座必须在同一容量约束下事务检查，避免候场成员被 AI 挤出开局容量。

创建者仍为真人房主并占真人席位。本阶段至少保留一个真人所有者席位；不增加只管理全 AI 房间的旁观者角色。所有真人后来主动托管时允许游戏在无在线连接情况下继续。

AI 的“就绪”是服务端计算的：策略版本可用、与锁定游戏兼容，才能 ready。不要伪造用户点击准备。添加/移除 AI、修改游戏/选项/人数/策略配置使真人准备失效；AI 就绪重新计算。开局需要全部席位已占、真人全部准备、AI 全部可运行、无候场真人。

房间 start 沿用原子开局：初始化游戏、保存所有真人/AI 固定参与者、版本锁、控制器配置并提交。调度只能在提交后启动；若提交后进程立即退出，恢复扫描也必须补上首个 AI 任务。

## 7. 控制权操作与权限矩阵

| 操作 | 允许者 | 条件 |
| --- | --- | --- |
| 添加/移除专用 AI | 房主 | waiting 且目标席位符合要求 |
| 选择内置策略 | 房主设置专用 AI；本人设置自身托管 | 策略在白名单、版本兼容 |
| 开启自身托管 | 真人席位所有者 | 对局 active、账户有效 |
| 收回自身控制 | 真人席位所有者 | 对局 active、目前 script |
| 操作他人托管/读取 AI 手牌 | 无此普通用户能力 | 房主也不例外 |
| 重试已阻塞的专用 AI | 房主 | 仅触发重新调度，不提供动作内容 |
| 重试自身托管 AI | 本人 | 不改变所有者 |
| 关闭对局 | 沿用房主权限 | 与动作/控制变更串行 |

托管可在本人回合或非本人回合开启。收回控制无需等 AI 完成，但必须等待短事务锁，而不是等待 AI 计算。托管不能修改游戏 phase、回合或手牌。

断线、刷新、会话到期不自动开启或关闭托管。已主动授权的托管独立于发起它的浏览器会话：登出、会话过期、密码重置后可继续；停用账户则阻止该账户席位新的 AI 提交并使旧任务失效，等待管理恢复或房主关闭。须说明这与第四阶段“停止客户端重试”并不矛盾，后台托管使用独立授权。

## 8. controllerEpoch 与竞态语义

控制变更用明确目标值 set human / set script，不用不幂等的 toggle。请求携带 requestId、expectedControllerEpoch；真正变更时在事务内 controllerEpoch+1。重复同请求返回原结果，不重复递增；无变化的同目标请求明确返回当前状态，不虚增 epoch。

同样的 game revision 可能经历 human → script → human，因此所有新真人动作也必须携带 expectedControllerEpoch。服务端验证当前为 human、本人拥有该席位且 epoch 匹配，防止切换前发出的真人请求在切换回来后意外执行。前端必须适配；旧客户端缺字段明确报协议错误，不猜测 epoch。

控制变更沿用 room → match → participant 的统一锁序，与游戏动作串行。默认只改变控制 metadata 与 epoch，不增加游戏 revision，不调用游戏 reducer，不消耗 RNG。额外 controller 状态版本用于实时合并，不能强行伪造一次游戏行动。任务状态另有单调 aiStatusVersion。

保证的并发边界：

- 若 AI 动作先提交，再收回，则已提交动作保留；收回不是撤销。
- 若收回先提交，则所有旧 epoch 的 AI 新提交拒绝，即使计算无法及时取消。
- 同 ID 的旧成功请求可按回执返回原结果，但不能被当作又执行了一次。
- 开启托管时如存在真人未知结果请求，先查询/同步；服务端锁序决定真实先后。界面不得宣称托管撤销了此前可能已提交的操作。

## 9. 游戏与策略扩展契约

平台调度器不理解颜色、数字或 targetSeatId。游戏扩展提供行动需求和安全决策上下文；策略模块定义 Color Match 的具体选择方法。

建议职责接口（伪代码，沿用现有 SDK 等价命名）：

```ts
type DecisionInput<View, Action> = {
  matchId: string;
  seatId: string;
  revision: number;
  controllerEpoch: number;
  decisionKey: string;
  view: View;
  legalActions: readonly Action[];
};

type ScriptPolicy<View, Action> = {
  id: string;
  version: string;
  decide(input: DecisionInput<View, Action>): Promise<Action>;
};
```

扩展应提供可行动座位/decisionKey，以及按座位生成的 View 与合法动作候选。平台可在可信规则层读取完整 state 来生成这些数据，但传给策略的只能是当前座位合法可见信息。决策上下文来自同一快照，不能混合两个 revision。

Color Match 动作空间小，本阶段可以列举全部合法候选；不要求所有未来游戏永远枚举所有动作。保留 query/schema 型动作描述的扩展方向，文档说明将来复杂游戏可提供按需候选。候选本身也必须符合信息权限，不能包含对手手牌 ID。

策略只返回一个 action；正常等待由调度器根据“无行动需求”处理，不能让 AI 自创 pass。每次状态推进后重新生成任务，待选目标是独立决策，不能一次计划跨越数个 revision 提交。

## 10. Color Match 策略与合法兜底

实现一个内置、确定性的 basic-v1 策略，覆盖所有已存在的可行动 phase。规则以仓库已验收实现为准，以下仅是合法候选的选择偏好：

1. 在合法出牌候选中，优先选择能保留较多同色后续手牌的牌；仅依据自己的手牌计算。
2. 平局按稳定的颜色/数字/实例 ID 顺序选择，不用游戏 RNG 打破平局。
3. 没有合法出牌但允许摸牌时选择摸牌。
4. 选择目标时，只在合法目标中按公开手牌数量最少优先，再按固定 seatIndex 打破平局。
5. 没有行动需求就不创建任务；有行动需求却无合法候选属于扩展契约错误，不伪造动作。

策略可更简单，但必须写明确定性排序、覆盖全部 phase，且不宣称最优。平台核心不得包含上述游戏偏好。

另提供独立、简单的 fallback：在当前任务同一快照的合法候选中选择稳定排序第一项，仍走统一动作验证。不得绕过规则强制摸牌、跳回合、改变手牌或自动判负。主策略失败才兜底；正常决策不做无意义重算。

若候选错误或兜底也失败，在有限尝试后将该席位调度状态置 blocked，显示安全原因、重试和真人收回入口。不能忙循环直到 CPU 耗尽。策略正确性测试须覆盖可完成整局的固定种子；随机对局超过测试步数上限应报告，不能伪造胜利或改规则保终局。

## 11. 隐藏信息与运行边界

策略输入使用可序列化、克隆且只读的 DTO，不包含 state 引用、数据库 client、registry 内部句柄、token、完整 RNG 或获取其他玩家视图的回调。主策略和兜底受同样限制。

AI 座位的私密视图只进入服务端策略执行器，不通过房主 HTTP/WS 返回。真人托管的本人可以正常看自己的 View，其他人仍只能看规则允许的公开信息。思考状态不包含拟出牌、候选动作、目标、输入或错误堆栈。

测试构造两份完整 State：保持该 AI 的 View 和合法候选相同，改变其不可见牌堆/对手手牌，策略结果必须相同。这验证输入隔离，不能只检查前端没显示手牌。

本阶段仅运行仓库内审核过的策略。worker 线程/子进程用于隔离计算和终止失控任务，并不等于可以安全运行用户上传的不可信 JS；不要新增上传、eval 或任意模块路径入口。

## 12. 持久任务模型

采用 PostgreSQL 任务表，内存队列只负责唤醒。复用项目已有可靠队列可以，但必须满足下面语义，避免为本阶段额外引入无必要的 Redis 服务。

| 字段/约束 | 用途 |
| --- | --- |
| taskId、matchId、seatId | 稳定任务与对局定位 |
| sourceRevision、controllerEpoch、decisionKey | 绑定决策所依据的状态与控制权 |
| policyId/version、policyHash | 精确策略锁定 |
| status | queued/running/proposed/submitting/succeeded/stale/cancelled/blocked |
| availableAt、attemptCount、deadline | 排队、有限尝试、超时 |
| leaseOwner、leaseUntil、leaseGeneration | 领取与过期任务的栅栏 |
| requestId、proposedAction、proposalHash | 冻结要提交的命令 |
| appliedRevision、safeErrorCode、timestamps | 恢复与诊断 |

逻辑唯一约束为 (matchId, seatId, sourceRevision, controllerEpoch, decisionKey)。同一决策被重复唤醒只得到一个任务。运行时故障重试增加 attempt，不生成第二个同意图任务。

任务表可能包含该座位私密 action，仅内部可读，不对外原样 SELECT *。不必长期存 View；恢复时从匹配 revision 的当前 state 重新投影。若当前 revision 已变化，旧任务标 stale 而不是使用新版 View 搭配旧标识继续计算。

## 13. 唤醒、领取与公平调度

在开局成功、游戏动作成功、控制变更成功后触发 reconcileMatch。它读取最新权威状态，为有行动需求且受 script 控制的席位创建唯一任务。

另提供启动扫描和周期补偿扫描（默认每 5 秒分页扫描 eligible 活跃对局/任务），补偿“事务提交后、唤醒前崩溃”。无人打开页面也要继续；不得依赖浏览器定时请求驱动 AI。

默认全局最多 4 个并行决策，同局最多 1 个；队列按 availableAt 和创建顺序公平处理，不递归同步运行完整一局，其他房间不得长期饥饿。每个决策让出事件循环。可配置最小显示间隔约 400ms，不在数据库事务里等待。

领取任务用原子条件更新或行锁，设置有限 lease 并递增 leaseGeneration；两个 worker 不能同时持有同一有效代次。同局多个未来行动需求不要求本阶段并行计算，保留遍历多个 seat 的接口而非写死 currentPlayerId。

## 14. 决策执行、超时与取消

任务领取后，短事务读取/核验 revision、epoch、策略和行动需求并生成输入，立即释放锁。所有策略计算在事务外进行。

默认主策略计算预算 2 秒，兜底 500ms；lease 15 秒，按实际运行环境配置。执行器必须能停止同步死循环，不能仅使用 Promise.race 给同一事件循环中的 while(true) 包超时。使用可终止的 worker 线程或子进程池，超时终止并回收槽位。验证后再决定是否需池化，不要求不必要的复杂优化。

取消信号用于尽早省资源，数据库 epoch/revision/leaseGeneration 才是提交前的最终防线。任务超时、worker 崩溃或租约失效后，旧 worker 即使返回也不得冻结结果或提交。后台计算没有直接写 match 的权力。

默认一次主策略尝试、一次兜底；暂态数据库失败使用有界退避，不算策略水平失败。恢复扫描不得清零 attemptCount 造成无限失败循环。管理重试有权限校验、幂等和冷却，不能绕过控制权。

## 15. 冻结提案、统一提交与原子完成

决策得到 action 后先校验结构，并在短事务中重新检查 task leaseGeneration、sourceRevision、controllerEpoch 和当前策略；条件满足才把 action、hash、requestId 持久化，进入 proposed。提案一经冻结，后续网络/进程重试使用完全相同内容，不重新选牌。

调度器再调用第四阶段同一个 command service。内部入口仅可由可信调度模块调用，不暴露一个让浏览器填 isAI=true 的免鉴权 HTTP 入口。

提交事务按统一锁序重新验证：对局 active、固定 seat、当前 controller=script、epoch 一致、任务身份与 fencing token、expectedRevision 一致、决策仍可行动、账户所有者未停用、策略版本可用。之后执行与真人相同的 validate/reducer/state schema、RNG 持久化和事件投影。

成功动作、回执和 task succeeded/appliedRevision 尽量在同一事务提交。若使用既有队列无法原子标任务完成，至少保证回执是唯一权威，重启先查回执再补 task 成功状态，不能重新执行。

为了防死锁，调度事务、控制变更、close、动作一致遵守 room → match → participant → task；单独领取 task 的事务提交后才进入 match 流程，禁止持有 task 锁再反向等待 match。

## 16. AI Actor 与幂等键迁移

第四阶段以 actorAccountId 为幂等主体；专用 AI 没有 account，必须显式扩展内部可信主体，而非挂靠房主。

推荐内部 Actor 为 human(accountId) 或 automation(matchId,seatId,controllerEpoch)。由认证适配器/任务调度器构造，客户端 body 不得决定可信 Actor。

回执幂等键采用 (matchId, actorPrincipalKey, operation, requestId) 的等价表达。human 旧记录回填为固定 human:<accountId>；automation 的主体由服务端固定序列化。使用结构化字段或无歧义编码，防止字符串碰撞。保留旧回执与查询行为，不丢失第四阶段的去重历史。

requestHash 绑定 expectedRevision、action、expectedControllerEpoch 等有意义字段。AI requestId 从持久 task/提案产生并固定。未知提交结果只能查回执或同请求重试，不能换 requestId、换 action；已冻结主策略提案结果未知时不得改成 fallback 提案。

主策略无效且尚未冻结/提交时可以选 fallback；已确定拒绝后的处理按错误类别结束旧请求，若确需新提案必须显式记录 attempt 与新 requestId，不覆盖旧回执。本阶段优先在冻结前完成候选校验，简化这一分支。

## 17. 收回控制与旧任务失效

控制变更事务原子写 controllerType、controllerEpoch、策略版本引用/授权，并持久化控制命令回执；把旧 epoch 任务标失效或由所有提交入口通过 epoch 拒绝。发取消通知是提交后的优化，不是正确性保障。

收回后 UI 获得新 epoch 和当前 View/动作描述，只有同步后才允许真人出牌。即使旧 AI 已经返回 proposed，也因 epoch 过期不能继续。若 AI 在收回前已成功，则回执保持成功，不能把历史任务改成“从未执行”。

控制改变不恢复过去手牌、不重置 phase，也不重置 AI 自己以外的席位。待选目标时托管，AI 只做合法目标选择；此时收回，真人继续选择目标。

控制事件有独立稳定 ID 和版本，不冒充游戏动作事件；公共信息仅包含座位、控制类型和安全状态。私密日志与待提交提案不广播。

## 18. 重启、崩溃和异常恢复

| 故障窗口 | 恢复要求 |
| --- | --- |
| 开局提交后、创建任务前 | 周期/启动扫描补建任务 |
| queued 后 API 退出 | 任务仍在 DB，重启可领取 |
| running 中 worker/API 退出 | 租约过期后有限重试，旧代次无权提交 |
| proposed 已存、提交前退出 | 重用冻结 action 和 requestId |
| 提交成功、回复丢失 | 查原回执，标成功，不重复动作 |
| 收回提交后、取消通知丢失 | epoch 阻止旧结果 |
| 对局结束/关闭 | 停止新任务，旧任务失效，不再推进 |
| 策略版本缺失/摘要不符 | 明确 blocked，不静默换新版本 |
| 数据库暂时不可用 | 暂停领取和提交，恢复后读 DB 权威状态 |

主动托管的策略版本在授权时精确固定，专用 AI 在开局时固定。若内置 fallback 是独立实现也固定版本。升级包不能改变旧局策略；恢复缺失版本后可继续，不能清空任务历史或重新 setup。

后台任务继续运行的条件是对局 active、控制授权有效、策略可用，不是 WebSocket 是否在线。禁止靠玩家刷新才能继续 AI。

## 19. API 与实时协议

以下为职责示意，沿用既有 /api/v1 与安全 envelope：

| 接口 | 用途与约束 |
| --- | --- |
| GET /games/:id/ai-policies | 返回兼容的公开策略描述，不返回服务端文件路径 |
| PUT /rooms/:id/seats/:seatId/bot | 房主给空位添加白名单策略；requestId + expectedRoomRevision |
| DELETE /rooms/:id/seats/:seatId/bot | 房主 waiting 时移除；幂等 |
| PUT /matches/:id/my-controller | 本人 set human/script；requestId + expectedControllerEpoch |
| POST /matches/:id/seats/:seatId/ai-retry | 本人或专用 AI 房主按权限重试 blocked 决策 |
| GET /matches/:id/view | 增加安全控制 metadata 和版本；私密 View 投影不变 |

所有浏览器写接口沿用 session、Origin、CSRF、大小限制和 schema。新增错误可包括 CONTROLLER_CONFLICT、CONTROLLER_NOT_HUMAN、AI_POLICY_UNAVAILABLE、AI_NOT_SUPPORTED、AI_TASK_STALE、AI_BLOCKED；内部租约失败不向无权限用户暴露任务详情。

实时传输可复用 match.snapshot，增加每席 controllerEpoch 和 aiStatusVersion。客户端分别按版本合并游戏、控制器和 AI 状态，不能因为 match revision 相同就丢弃“已收回控制”。旧思考状态不得覆盖较新已完成/真人状态。公共状态通知经参与权限校验；控制命令结果未知也需幂等查询或原 ID 重试。

## 20. 前端页面与操作体验

房间页：空位显示房主可用的“添加脚本 AI”；AI 席位显示名称、策略、就绪或不可用原因，waiting 可移除；普通成员不能看到可执行的管理按钮。添加 AI 后明确其他真人需重新准备。

游戏页：真人本人显示“开启托管”；开启后显示“托管中”和始终可用的“收回控制”入口，正常出牌按钮禁用。其他玩家看到该席位的控制类型，不获得其私密候选。AI 状态显示等待回合、排队、思考、提交、恢复中或异常，不把排队时间伪装为推理时间。

本人点击收回后显示“正在收回”，等服务端提交确认及最新快照再开放动作；不能即时宣称已停止所有 AI。若竞态中 AI 已先走一步，刷新到已提交局面并简明解释。可说明托管会持续到主动收回，关闭页面不会结束托管。

异常提供安全原因、重试、本人收回；专用 AI 失败不允许房主手动替它指定牌。390px 手机与 1440px 桌面均能添加 AI、托管、收回和完成整局；按钮支持键盘操作。

## 21. 数据迁移、配置与可观测性

扩展 seats/participants 的 occupantKind=human|bot，真人 ownerAccountId 非空、专用 bot 为空，并有数据库约束。迁移已有席位为 human，保持 account 外键、历史记录和权限；不要因放宽 nullable 失去基本完整性。ready 对 bot 采用服务端计算，不复用依赖真人账户的校验。

增加策略引用、task 表、principal 回执和必要索引：可领取任务(status,availableAt)、过期 lease、match/seat 查询、唯一决策键。迁移支持空库和第四阶段已有对局；已有 controllerEpoch 不重置。旧真人对局默认仍由 human 控制，绝不自动托管。

配置至少包括全局并行、同局并行、决策超时、lease、扫描周期、队列上限与重试冷却。默认数字来自本文件，可按部署校准并记录。达到容量上限应排队/明确不可用，不丢失需执行的决策。

日志记录 taskId、matchId、seatId、epoch、revision、policy 版本、attempt、耗时、成功/兜底/过期/blocked；不默认记录 View、proposedAction、私密候选或 RNG。监测队列长度、最老等待时间、超时率和过期任务数。调试钩子仅测试环境可用。

## 23. 测试方法与故障注入

使用真实 PostgreSQL、独立连接、两个隔离浏览器账户和一个非成员账户。API/worker 用可真正终止的子进程或线程；不要只 mock Promise 超时来证明死循环可停止。

测试屏障设置在领取后、计算后冻结前、冻结后提交前、COMMIT 后任务确认前、收回事务提交后取消前。并发动作通过屏障精确排序，不能依赖偶然 sleep。

测试策略提供 timeout、throw、非法 action、迟到结果四种 fixture，仅测试环境注册。正式策略目录不得让用户选这些 fixture。

至少运行 2、3、4 人配置的真人+AI 正常流程；自动化批量模拟用固定的一组种子并记录 seed/步数/结果到受限测试报告。测试步数上限防挂死，不是生产新增强制平局规则。针对多房间排队记录最长等待，证明一个持续运行的对局不会阻塞其他房间。
